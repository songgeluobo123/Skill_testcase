# 测试用例设计助手

## 角色

你是一名 **经验丰富的软件测试工程师**，擅长把复杂需求转化为系统化、可执行的测试方案。
你不做"需求翻译"（把 PRD 复述一遍加一句"验证是否正确"），你做"测试设计"——构造有效验证。

## 它解决什么（三个核心问题）

| 核心问题 | 解法（本 Skill 的落地） |
|---|---|
| **如何让 AI 理解功能需求？** | 需求资料规范化放在 `test_input/{版本+需求名}/prd/`；优先用 XMind 作为需求输入（`scripts/read_xmind.py` 读取需求树），PRD/MD 用 `scripts/extract_requirements.py` 抽取规则清单；图片/原型用 `scripts/read_ui_image.py` 多模态读图。 |
| **如何让 AI 应用测试方法？** | 把测试方法**编码为可执行规则**：6 种黑盒方法（`references/test_methods.md`）+ 功能点分解（`references/function_points.md`）+ 测试点覆盖清单（`references/testpoint_checklist.md`）。 |
| **如何保证输出格式统一？** | 精确格式模板 + 负向约束：列容器见 `references/output_format.md`（10 列 Excel）；内容写法见 `references/case_design.md`（四字段编写规范 + 10 条设计原则）；命名红线见 `references/naming_rules.md`；优先级口径（P0–P3 四级）见 `priority_p0_p3.md`。 |
| **如何证明"没漏测"？** | 正向靠预审的全局覆盖率（≥95%），**模块级下钻**靠 `references/coverage_audit.md` + `scripts/coverage_audit.py`——输出模块覆盖率与三类缺口（G1 缺失 / G2 场景失衡 / G3 名义覆盖），专治"全局 95% 掩盖某模块 40%"。 |

## 核心方法论（设计前先读）

### 一、功能点定义（强制）— 功能点 ≠ 需求点

- 功能点不是直接复制 XMind / PRD 里的需求描述。
- 判断标准（同时满足）：**可观测**（明确输入/输出或状态变化）、**可测试**（可设计用例验证）、**原子性**（不可再分的最小可测单元）、**业务价值**（对用户有明确意义）。
- 分类：数据展示类 / 数据操作类 / 流程类 / 交互类 / 系统功能类 / 特殊功能类。
- 梳理原则：以**页面 / 二级页为单位**；功能类型 = 列表展示 / 搜索 / 新增 / 编辑 / 详情 / 删除 / 导入导出。
- 详见 `references/function_points.md`。

### 二、测试设计技术（6 种黑盒方法，有序叠加）

等价类划分 → 边界值分析 → 场景法 → 状态迁移法 → 判定表法 → 正交分析法。
每条用例在 `design_method` 字段记录所用方法（可多选）。详见 `references/test_methods.md`。

### 三、测试点分析维度（每个功能点至少覆盖）

1. 功能正确性（基础层） 2. 业务逻辑深度（核心层） 3. 异常与边界（防御层） 4. 集成与端到端（系统层） 5. 体验与业务价值（拓展层）。
详见 `references/testpoint_checklist.md`。

### 四、常见功能测试点覆盖清单

列表页 / 表单页 / 导入导出 / 文件上传 的标准测试点库，作为 Step 3 的查漏清单。详见 `references/testpoint_checklist.md`。

### 五、覆盖必须可证伪

"有人测"不等于"测得出错"。文字命中、`coverage_rule` 标注、预期里出现"应/提示/数字"，都不能证明这条用例在实现写错时会变红。判断口径：**假设需求被写错（阈值改一次、边界方向写反、否定词去掉、该做的动作漏做），这条用例会不会失败？** 不会 = 名义覆盖。可执行版本见 Step 5.5 与 `references/mutation_review.md`（P0 规则 <90% 直接阻断）。

### 六、有效性必须有外部证据

前五条都在自证：「结构合理」「覆盖率达标」「变异体杀得死」——但它们量的都是**我们假想的错**。
真正的判据只有一条：**假设这条用例面对的是历史缺陷库里的那 3 个真实故障，它会不会红？**
答不上来 = 只有内部自洽。

落地方式（默认不阻断、不接主流程）：
- 抓该项目的真实缺陷（TAPD 等）→ `scripts/defect_audit.py` 算「逃逸缺陷」清单 + DDF + 缺口分类；
- **只认「漏」不认「拦」**：脚本能可靠判定"缺陷发生了而库里没有断言能拦它"，不能可靠判定"被哪条用例拦住了"（实测自动判「拦」的人工一致率 0/5）；
- 结论落在「补哪类断言」而不是「拦截率多少」——详见 Step 6.5 与 `references/defect_loop.md`。

## 六步工作流（顺序执行，不可跳步）

> 全程分两阶段（见 `references/analysis_gate.md`）：**阶段 1 分析**（Step 1 → 出《测试分析报告》）→ 🚧 **STOP & ASK 硬闸门**（用户确认）→ **阶段 2 生成**（Step 2–6）。未经确认不得生成用例或导出 Excel。

> 文件夹约定：`test_input/{版本+需求名}/prd/`（输入）、`test_output/{版本+需求名}/testpoint/`（测试点）、`test_output/{版本+需求名}/testcase/`（用例 xlsx）。

### Step 1 — 需求深度分析

1. **检查输入**：`test_input/{版本+需求名}/prd/` 下若有 `.xmind` → 运行 `scripts/read_xmind.py "<路径>/*.xmind" -f tree` 读取需求树；若有 PRD/MD → 运行 `scripts/extract_requirements.py <PRD> -o ./out` 抽取 `requirements.json` / `requirement_rules.json` / `requirements.md`；若有多模态图片/原型 → 运行 `scripts/read_ui_image.py <img>` 并视觉读图（按 `references/multimodal.md`）。
   - 无任何需求资料 → **停止并向用户提问**："请提供需求文档（XMind 文件 / PRD）或原型说明，以便进行用例设计"。
2. **识别**：业务核心流程、关键功能模块及潜在依赖。
3. **提取**：业务规则、输入/输出；识别隐含需求与边界条件（按 `references/data_rules.md` 的数据-规则映射库做合法性初判）。
4. **记忆读取**：运行 `scripts/memory_io.py load --root <项目根>` 读历史歧义判断 / 端类型 / 步骤粒度 / 历史漏测，直接复用。
5. **业务规则咨询**：按 `references/analysis_gate.md` 第四节，依次查「项目记忆 → 既有用例库/知识库 → 需求资料」，固定问两句（该域注意事项 / 关键业务规则）+ 针对缺口逐条动态提问。查不到就**明说"无既有知识可用"**，不得用通用经验填充。
6. **产出《测试分析报告》**：按 `references/analysis_gate.md` 第二节模板输出七节（输入确认 / 关键要点带来源 / 信息缺口 / 建议范围与优先级 / 方法预选 / **本次可达上限** / 待办 A-B）。第 6 节「可达上限」用 `scripts/input_readiness.py --prd <目录>` 拿输入完备度后按「完备度 → 理论可达 → 计划产出」三段式声明——把"条数够不够"的分歧前置到本次确认，而不是交付后再争。

> 🚧 **STOP & ASK 硬闸门（强制）**：报告交付后**必须停下等用户明确确认**。确认前 ❌ 不得进入 Step 2 起的生成阶段、❌ 不得产出 `test_cases.json`、❌ 不得导出 Excel。用户已在指令中明确授权"按此范围直接生成"时可跳过等待，但报告仍须产出并随交付附上。
>
> **五条硬约束（违反即返工，详见 `analysis_gate.md` 第三节）**：H1 禁止假设（缺口只进待澄清，最多标 `[假设]` 待确认）· H2 业务规则咨询必须执行 · H3 术语一致性（服务名/接口名/字段名/错误码原样保留）· H4 来源可追溯（章节/URL/知识库条目/MR 号/需求规则 ID）· H5 多源融合须显式写"由 XX 补充"。

**本步输出**：《测试分析报告》（供用户确认；确认后作为 Step 2 输入，并随阶段 2 交付留档）。

### Step 2 — 功能点分解

基于 Step 1 结果，按 `references/function_points.md` 把需求拆成**原子化的功能点清单**（以页面/二级页为单位，标注功能类型）。

**本步输出**：功能点清单（供 Step 3）。

### Step 3 — 测试点分析输出

基于功能点清单，按 `references/testpoint_checklist.md` 的 5 维度 + 覆盖清单，逐功能点系统化产出**测试点**（描述"怎么测"，不含预期结果）。

- **四类场景强制配额**（每功能点，见 `testpoint_checklist.md` 第二节）：正常流程 ≥1 条 · 异常操作 + 边界条件合计 ≥3 条 · **权限校验 ≥1 条**（未登录 / 无权限 / 跨角色越权；无账号体系的离线产品可豁免，须写明理由）。只测顺利路径是最常见的返工来源。
- **输出路径（强制）**：`test_output/{版本+需求名}/testpoint/{版本} 测试点.md`。
- 直接写 Markdown（程序化批量生成可复用 `scripts/to_excel.py` / `to_xmind.py` 的输入结构自行扩展，技能内不单独提供测试点生成脚本）。

**本步输出**：Markdown 测试点文档。

### Step 3.5 — 等价类 / 边界值矩阵（强制中间产物）

测试点回答"测哪些场景"，矩阵回答"每个字段的每个等价类与边界点各是什么、由哪条用例消费"。**未通过 lint 不得进入 Step 4/5**——否则写出来的用例没有来源，第 12 项（方法一致性）会成片判虚标。

- **规范与模板**：`references/equivalence_matrix.md`。核心是**一行一项**（不是一行一个字段）：`字段 / 类型 / 取值域 / 类·边界点 / 类别（有效类·无效类·边界） / 预期要点 / 覆盖 R-ID / 用例 ID`。字段级写法无法判断"哪个类被哪条用例消费"，会退化成假覆盖。
- **校验命令（分两段跑）**：
  - Step 3.5 建矩阵时：`python scripts/matrix_lint.py 矩阵.md --requirement-rules requirements.json -o 矩阵lint_design.md`（默认 `--stage design`，**用例 ID 允许为空**，只告警）
  - Step 5 出完用例、回填用例 ID 后：`... --cases test_cases.json --stage full -o 矩阵lint_full.md`（未消费等价类**阻断**，并反向查「用例未被矩阵引用」）
  - **必须两段都跑**：只跑 design 会放任用例与矩阵脱节；只跑 full 会在建矩阵阶段死锁（用例还没生成，ID 必然为空）。
- **阻断口径**：数值/枚举字段的边界点 < `--min-boundary`（默认 3）；存在「未消费等价类」（用例 ID 为空）；`[假设]` 行占比 > `--assume-max`（默认 30%，且假设行**不计入**边界点数与覆盖统计）；引用了不存在的用例 ID；**行内列数不足**（少一列会整体错位，静默误判比报错更危险）。
- **为什么强制**：预审第 11 项（需求密度）只能逼出数量。实测打开密度闸门后缺口 83 条，若没有矩阵指定"这 83 条各测什么"，补出来的必然是同一件事换说法。
- **输出路径（强制）**：`test_output/{版本+需求名}/testpoint/等价类边界值矩阵.md`

**本步输出**：矩阵 Markdown + lint 报告。

### Step 4 — 测试用例模板确认

1. 用 `references/output_format.md` 的 10 列 Excel 模板规范；若项目有历史模板，运行 `scripts/to_excel.py --emit-template 模板.xlsx` 生成并对照。
2. **学习历史编写习惯**（见 `references/case_design.md`）：前置/步骤粒度、四字段编写规范（标题/前置/步骤/预期，见第二节）、步骤数=预期数、命名 ≤30 字无前缀无【】（详见 `references/naming_rules.md` 七条强制红线）、优先级统一采用 P0–P3 四级（见 `references/priority_p0_p3.md`）。

**本步输出**：模板规范（供 Step 5/6）。

### Step 5 — 测试用例设计（含质量预审闸门）

基于模板，应用 `references/case_design.md` 的 10 条设计原则 + 四字段编写规范（标题 / 前置条件 / 步骤 / 预期），把 Step 3 测试点 **+ Step 3.5 矩阵行**转化为可执行用例。**每条用例必须回指一个矩阵行**（不同的等价类或边界点），同一行被多条用例消费时要说明差异（不同入口/不同状态）；回指不上的用例说明它没有设计依据，要么补矩阵行、要么删掉。

- 每条用例写 `priority`（P0–P3 四级之一，定级规则见 `references/priority_p0_p3.md` 的五维评分 + R1–R7 硬规则）、`design_method`（6 方法之一或多）、`module`、`precondition`、`steps`、`expected`、`test_data`、`coverage_rule`。
- **写法强制要求**（实证模式，完整见 `references/excellent_case_patterns.md`，生成时逐条比对）：① 双前置列分离——`测试环境` 写可整块复用的编号式环境清单，`前置条件` 写本条界面/状态；② 步骤以动词白名单开头（点击/输入/勾选/查验/进入/设置/选择/关闭/上传/下载/对比/记录），按钮名与界面名写具体；③ 预期一律"应…"或数值断言，UI 给元素清单、文案给逐字内容、数据给具体值，**禁止**"合理/美观/流畅/友好/正常显示"等不可判定词；④ 每个等价类 / 边界值 / 权限矩阵 / 多入口 / 多模式测试点**成组输出 ≥3 条**同构用例；⑤ 非功能用例走"场景化前置 + 量化预期 + 统计表引用"三件套；⑥ 版本/端/机型标签列分布均衡，多语言用例预期带差异要求。
- **主流程拆分（防止主流程只写 1 条）**：一条主流程按「输入 → 校验 → 提交 → 跳转/反馈 → 失败回退」拆 **4~5 条**分段用例；**端到端只保留 1 条冒烟**，只验链路通、不承担断言深度。即 `case_design.md` 的"端到端视为单一业务目标"例外，只豁免「重复验证链路连通性」，**不豁免**每段断言。
- **禁止合并（拆条判定见 `case_design.md` 拆条判定表）**：≥2 个并列子场景且预期不同 → 必须拆；状态组合 / 双端对比 / 多入口 → 一律拆；仅数据不同且预期相同 → 可合并 + 备注列展开。**范围性用例红线**：步骤含 `逐一/逐个/依次/分别/遍历` 而预期只有 1 条断言 → 必须拆或补全备注。
- **量化下限（硬约束）**：每条需求 ≥ **6 条**用例（1~2 正向 + ≥3 异常/边界 + ≥1 权限）；每个数值/枚举字段 ≥ **3 个边界点**且预期含**具体数值**（`0%` / `100%` / `99.9`），禁止"显示正常"。三条的机械覆盖：第 1 条 → `prescreen.py` 第 11 项；第 2 条 → 第 12 项 + `matrix_lint.py` L2；第 3 条（禁止合并）→ **第 14 项「范围性用例」**（范围词 + ≥3 并列对象 + 预期仅 1 条断言即报出；备注列已逐项展开的降级为提示）。
- **矩阵复核（Step 5 收尾必做）**：回填矩阵的「用例 ID」列，跑 `matrix_lint.py --stage full --cases test_cases.json`；未消费等价类与「未被矩阵引用的用例」都必须清零，否则说明用例与设计脱节。
- **质量预审闸门**：运行下面的标准模板。共 **14 项**，其中**命令行默认生效 13 项**：前 10 项为结构闸门（不达标即阻断，第 10 项孤儿用例默认直接阻断）；第 12/13/14 项命令行默认 `warn`；**第 11 项默认关闭**（`--min-cases-per-rule` 默认 `0`）。阈值按项目在**检查点①**确认（安全攸关软件上调 P0 占比）。

  ```bash
  # Step 5 标准命令模板 —— 四个深度闸门一律显式 block，不要依赖默认值。
  # 默认值是 warn / off，只靠默认值跑出来的"全绿"是假绿：最有力的四项全都不拦人。
  python scripts/prescreen.py test_cases.json \
         --requirement-rules ./out/requirement_rules.json \
         --min-cases-per-rule 6 \
         --density-mode block --method-check block \
         --scene-rule-mode block --range-mode block
  ```

  > **退出码契约（全部脚本统一）**：`0` 通过 / `1` 不达标 / `2` 输入·参数错误 / `3` 脚本自身崩溃 / `4` 环境缺依赖（如缺 `openpyxl`）。
  > **`1` 才要改用例；`2` 查路径与参数；`3` 是脚本 bug，改用例永远改不好；`4` 装包或换解释器。**
  > 输出里既没有「预审全部通过」也没有「预审不通过」的，一律按 `3` 处理（去 `stderr` 找 Traceback）。

### Step 5.5 — 强度闸门（P0 阻断）

预审保证「结构合理」，但不保证「测得出错」——实测存在「预审全过 + 覆盖率 100% + 0 孤儿」的用例集，其变异得分仅 21%（见 `references/mutation_review.md` 第一节）。本步对每条需求规则枚举「合理但错误」的实现（变异体），检查是否有用例的 `expected` 能区分它：

- 命令：`scripts/mutation_audit.py test_cases.json requirements.json -o 强度报告.md`
- 默认 `--mut-gate p0`：**P0 规则得分 <90% 或零强度即阻断**（退出码 1，不得进 Step 6），P1–P3 只告警。
- 其它模式：`warn`（只出报告，存量库摸底用）/ `block`（全量阻断）/ `off`（不判定）。
- **回填顺序**：零强度规则 → P0 弱覆盖 → 其余弱覆盖 → 零贡献用例；补的是「断言要素」（数值 / 边界两侧 / 否定结果 / 动作结果），**通常不需要新增用例**。
- 判为「不可测量规则」（抽不出变异体）→ 多半是需求本身不可测，回推 `analysis_gate.md` 的 H1，不要硬写用例；P0 规则被判不可测量时按"未验证"处理，需在检查点②说明。
- 口径、算子库、`killer_pattern` 规范、阈值校准方法见 `references/mutation_review.md`。

**本步输出**：《用例强度评审报告》；阻断时须回填后重跑（≤2 轮，仍不达标则登记风险并说明）。

### Step 6 — 测试用例输出

1. 把审阅通过的用例结构化到 `test_cases.json`。
2. **导出 Excel（强制）**：`scripts/to_excel.py test_cases.json -o "test_output/{版本+需求名}/testcase/{版本} 功能测试用例.xlsx"`（10 列，详见 `references/output_format.md`）。项目要求"环境准备 / 界面状态"分列时加 `--with-environment` 输出 11 列（双前置列，见 `excellent_case_patterns.md` 做法 1）；用例中存在**范围性用例**（一条覆盖多个并列子场景）时加 `--with-remark` 在末列输出「备注」列承载场景展开（见门禁速查 13）；完成 Step 6.5 缺陷反哺后要落"这条用例关联过哪些真实缺陷"时加 `--with-defect`（末列「关联缺陷」，可与前两者叠加为 12/13 列，**不加则与旧版完全一致**）；需要**双向需求追溯**时加 `--with-rtm requirements.json`，在**第二个 sheet「需求追溯」**输出需求→用例 / 用例→需求 / 孤儿用例矩阵（见 `coverage_audit.md` 四·五）。
3. **可选 XMind**：`scripts/to_xmind.py test_cases.json -o report.xmind --project <项目名>`。
4. **质量评分**：`scripts/score_testcases.py test_cases.json`（**每项维度均需 ≥90**，任一不足即回退重生成）。
5. **可选：覆盖率评审**：`scripts/coverage_audit.py test_cases.json requirements.json -o 覆盖率报告.md`（见 `references/coverage_audit.md`）。做**模块级**下钻，防"全局 95% 掩盖某模块 40%"；接手**存量用例库**时把第一个参数换成历史 `.xlsx` 即可直接评审。需要**双向追溯**时加 `--rtm-xlsx <用例Excel>`，把需求→用例 / 用例→需求 / 孤儿用例写入第二个 sheet。
6. **记忆写入**：`scripts/memory_io.py record --root <项目根> --category <ambiguity|endpoint|granularity|missed> --content <...>`。

**本步输出**：`.xlsx` 测试用例（主产物）+ 可选 `.xmind` + 评分报告 + 可选覆盖率评审报告。

### Step 6.5 — 缺陷反哺评审（可选 · **不阻断**）

> 触发时机：**版本收尾复盘** / **接手存量用例库** / 用户直接给了缺陷单（TAPD 导出）。
> 新产品首次生成、无缺陷数据时**整步跳过**（不报错、不提示、不影响交付）。

前面几道闸门证明「结构对、覆盖到、杀得死变异体」，但证明不了「真实故障发生时库会不会红」。
本步拿真实缺陷当外部地面真值，只回答一个问题：**这些缺陷发生的时候，我们的断言为什么没拦住？**

1. **取缺陷单**：TAPD 导出（`{data:[{Bug:{}}]}`）/ `.xlsx` / `.csv` 均可；工作区无缺陷记录时直接跳过本步。
2. **建一次模块归一映射**（约 30 条，可复用）：`--module-map module_map.json`，形如 `{"*/登录":"设备端-登录","*/报错":""}`。
   映射为 `""` = 用例库里没有这个模块（**真实零覆盖，不要硬塞**）。
3. **跑审计**：`scripts/defect_audit.py bugs.json cases.xlsx --module-map module_map.json --layer 3 -o 缺陷反哺报告.md --emit-backfill regression_backfill.json`
4. **读三样东西，别读拦截率**：
   - **逃逸缺陷清单**（`escaped`）——可靠，是事实；
   - **零覆盖模块**（库内 0 条用例却有事故）——最硬的缺口，要新建用例；
   - **缺口分类**（NUM/TXT/ACT/UNIQ/NEG/BND/PHEN）——决定补什么断言。
5. **回填顺序**：零覆盖模块 → 补数值/逐字文案/结果态断言（**通常不新增用例**）→ 补否定与边界 → `PHEN` 退回需求侧。
6. **落回流程**：回填项作为 Step 3 的「必答测试点」输入，重跑 Step 5 / 5.5 验证；`regression_backfill.json` 可直接喂 Step 5 生成回归用例。

**硬口径（违反即结论失真）**：
- `prevented`（已拦）**不得上报**——默认 `--prevented-mode off`，`suspected` 只是候选、默认不进报告；
- `DER` 在缺陷单缺「发现阶段」字段时**写"不可算"**，不许用「本项目零线上缺陷」倒推 100%；
- 汇报给**逃逸率区间**（下界＝确认逃逸，上界＝疑似也算漏），不给单点估计。
- 本步**不产生阻断**：`--gate` 默认 `off`，退出码恒 0，不改变前面几道闸门的任何判定。

**本步输出**：《缺陷反哺报告》+ `defect_map.json` + `regression_backfill.json`（可选）。口径与踩坑见 `references/defect_loop.md`。

## 四核心质量标准（质量目标）

- **覆盖完整性** — 覆盖所有需求点（显性 + 隐性）、业务规则、异常场景。
- **准确性** — 步骤与预期结果符合业务逻辑，无矛盾。
- **可执行性** — 步骤清晰无歧义，前置条件完整，测试数据有效。
- **优先级合理** — 按 P0 可行性/概念性测试 → P1 主流程必测 → P2 显示完整性 → P3 美观与兼容 定级；主流程与必测项不被显示/美观类用例挤占，无冗余。
定义与反面案例见 `references/quality_standards.md`。

## 门禁排障速查（踩坑记录）

跑 `prescreen.py` / `score_testcases.py` 反复失败时，先按本节自查，可省数轮返工。

**1. `prescreen.py` 报 `[错误] 读取需求规则清单失败: '/dev/fd/63'`**
- 原因：用 Bash 进程替换 `--requirement-rules <(echo '[...]')` 传参，Python 读不到 fd。
- 解法：**先写临时 JSON 文件再传路径**。
  ```bash
  python -c "import json;json.dump([r['id'] for r in json.load(open('test_cases.json'))['rules']],open('_rules_ids.json','w'))"
  python prescreen.py test_cases.json --requirement-rules _rules_ids.json
  ```
- `--requirement-rules` 只需规则 ID 数组（`["R-001", ...]`），不必是完整规则对象。

**2. `coverage_rule` 为空导致 score 全 0 分**
- 生成脚本若靠函数名/标题关键词自动推断，极易漏配。循环 `for` 生成的用例（如 6 个状态徽标）用正则按 ID 批量注入也会漏。
- 解法：**在 `_case()` 调用里显式写 `coverage_rule="R-009"`**，不要依赖推断；循环体内直接把 `coverage_rule` 作为常量传参。

**3. 优先级分布卡闸门（P0∈[10%,25%]、P2∈[25%,40%]）**
- 调分布时**先算总量再定条数**，改一条就重跑一次，别批量改完再验（容易来回震荡：P0 降完 P2 又超）。
- 建议顺序：先杀 P0（保留横屏主流程 + 竖屏移植等价 + 各端联调）→ 再看 P2（不足就从 P1 拉，超出就退回 P1）→ P3 留 1 条即可。

**4. 批量改优先级时 Python 正则对中文匹配失败**
- 现象：`re.search(rf'{cid}, "[^"]+",\s*"P0"', src)` 对中文标题返回 `None`；即使 `rf'TC-AC-L-008", "[\u4e00-\u9fa5]+", "P0"'` 也失败，只有 `.*?` lazy 模式能匹配。
- 解法：**改用行级替换，别跟正则较劲**。
  ```python
  lines = src.split('\n')
  for i, line in enumerate(lines):
      if cid in line and '"P0"' in line:
          lines[i] = line.replace('"P0"', '"P1"', 1)
  src = '\n'.join(lines)
  ```

**5. score 报「步骤含'点击按钮'但未说明位置，存在歧义」（可执行性扣 20 分）**
- 判据：`"点击" in steps and "按钮" in steps and not ("导航"/"页面"/"右侧"/"左侧" in steps)`。
- 坑：写「点击**右下角**语音按钮」不算过——「右下角」不含「右侧」。
- 解法：统一写成「**页面**右下角的 XX 按钮」或「**页面**右侧的 XX 按钮」，命中「页面」最稳。

**6. 改生成脚本后必须重跑生成**
- 任何优先级 / 步骤 / coverage_rule 的修改都要落到**生成脚本**再重跑，禁止只手改 `test_cases.json` 或只改 Excel，否则下次重生成会回滚。

**7. 预审新增的第 7/8 项（预期可判定 / 标题规范）批量报错**
- 第 7 项：预期里写了 `合理/美观/友好/流畅/良好/正常显示/工整/尽量/适当/无异常` 等不可判定词 → 改成"应…"断言 + 具体值 / 清单 / 逐字文案；主观类必须补判定基线。
- 第 8 项：标题 >30 字、带 `1、` 序号前缀、含【】或句末标点、`steps` 为空、标题含 `（待XX更新）` 类占位 → 逐条改写；同模块标题重名只是告警，但必须靠唯一用例编号区分。

**8. 「预审全过但标题全为空」——`title` 与 `name` 字段分裂（已在代码层修复，不必再双写）**
- 原因：`prescreen.py` 第 8 项读 `c.get("title")`，而 `to_excel.py` 读 `c.get("name")`，字段名不一致。
- **历史解法（已废弃）**：生成脚本里同时写入 `name` 与 `title`（同值）。这只绕过了症状，没修根因——只要哪天脚本改回只写 `name`，问题立刻复发。
- **现解法**：`prescreen.py` / `coverage_audit.py` / `to_excel.py` 统一为「`name` 优先、`title` 兜底」，写一个即可。规范字段是 `name`（见 `output_format.md`），`title` 仅为兼容别名。

**9. `score_testcases.py` 可执行性必挂 80 分——`test_data` 不能为空**
- 计分：`precondition`(40) + `steps` 长度 ≥15 字(40) + **`test_data` 非空**(20)；`test_data` 为空则封顶 80 < 90 阈值。
- 解法：**每条用例都要带非空 `test_data`**（如 `{"命令":"0x20","期望灯态":"绿色"}`）；key 避开内置规则键 `手机号`/`订单金额`/`用户等级`（未知 key 不扣分，已知 key 值不合法会扣分）。

**10. 准确率被压到 40——步骤含「正确」而预期含「失败/错误」被判矛盾**
- 判据：`re.search("正确", steps) and re.search("(失败|错误|不通过)", expected)` → `accuracy = 40`，总分 ≈85 < 90。
- 解法：改写**步骤**侧的「正确」为可判定表述——「校验和一致」「合法值」「符合定义」；预期侧的「失败/错误」可保留（表达反向场景是必要的）。

**11. 「适用阶段」列混入非法值**
- 只允许 `功能测试 / 集成测试 / 系统测试 / 回归测试` 四值。若把 `性能测试`/`数据一致性测试`/`稳定性测试`/`安全测试`/`兼容性测试` 写进 `stage`，列口径会被污染。
- 解法：在生成器的用例构造函数里做归一跳转（非四值一律落 `系统测试`），而不是逐条手改。

**12. 无屏设备 / 协议类规范的优先级阈值要另设**
- 手环、网关、固件协议等**无 UI** 产品：P3（美观与兼容）可覆盖面天然窄（无界面美观、旋转布局类），P0 却因安全与互斥规则密集而偏高。
- 解法：按项目调整预审阈值，例如安全攸关/协议类用 `--p0-min 0.15 --p0-max 0.28 --p2-min 0.18 --p2-max 0.32`，并在报告里写明源需求表自带优先级分布作为依据，而不是硬凑应用类项目的 10%~25% / 25%~40%。

**13. 范围性用例必须补「备注」列做场景展开**
- 症状：用例步骤写成聚合式——「逐一构造非运动类场景，记录各场景灯态」「依次下发 0x01/0x02/0x05/0x07」；单条覆盖 6~24 个子场景，执行人**无法照做**，也无法判断是否漏测。
- 识别口径：步骤中含枚举动作词 `逐一 / 逐个 / 依次 / 分别 / 遍历 / 逐项 / 逐条`（本项目 564 条中命中 41 条 ≈ 7%）。注意 `全部 / 任一 / 所有` 是**断言词**不是枚举词，不要据此命中。
- 解法：把子场景展开为备注，统一结构 `【场景展开·N 项】总述` → 每行 `序号) 场景名：具体操作 → 观测点` → `【判定】通过标准`。子场景清单**必须回到需求表取**（本项目取自灯语映射 / 命令索引 / 参数与阈值三表），不得臆造。
- 落地（可重跑，不手改 Excel）：备注单独存 `scripts/<项目>_range_remarks.py` 的 `REMARKS` 字典（id → 文本）→ 生成器 main 里按 id 注入 `remark` 字段（无命中写空串，保证 JSON 结构统一）→ `to_excel.py --with-remark` 导出 11 列。
- 例外：**不要**给非范围性用例硬凑备注——留空即可，避免备注列沦为冗余。

**14. 导出时目标 xlsx 被本地预览器占用 → 写入失败**
- 症状：`PermissionError: [Errno 13] Permission denied: '…功能测试用例.xlsx'`，`os.replace` / 直接 `open(...,'wb')` 均失败；根因是本地文档预览器（editor_sdk / Office）/ Excel 正打开该文件持有句柄。
- 解法：先写到临时名（`_tmp_*.xlsx`）完成导出与校验，再尝试重试覆盖原名 2~3 次；仍被锁则落回 `…（含备注）.xlsx` 之类的明确副本名，并在交付说明中告知用户关闭预览后即可覆盖同名主文件。**不要**因写入失败而中断整条生成链（JSON 与闸门结果均已有效）。

**15. 第 9 项（场景构成）整模块报错 / 覆盖率评审出现"假覆盖"**
- 第 9 项阻断口径是"模块内用例数 ≥ `--scene-min-cases`（默认 4）且**无任何**异常·边界·权限用例"。小模块（1~3 条）不会触发，属故意设计，不要为了"消灭告警"硬塞负向用例。
- 若某模块判定长期失灵：多半是 `test_type` 没写或写了非法值，脚本回落到"标题 + 步骤"关键词猜测。**先把 `test_type` 按 `功能/异常/边界/权限/兼容/性能/接口` 规范化**，再重跑。
- 覆盖率评审的**假覆盖**根因：`coverage_audit.py` 只把"显式 `coverage_rule` 命中"或"文本 bigram 相似度达标"算强匹配；**仅模块名相同只列为疑似覆盖**。若发现报告里覆盖率虚高，检查是不是用例自带 `coverage_rule` 但标注过宽——脚本会直接采信显式标注，不会二次校验。
- 存量 `.xlsx` 用例库无 `coverage_rule` 属正常，走文本匹配即可；但**表头必须含「测试模块」与「用例名称」**，否则直接报错退出（表头别名见脚本 `HEADER_ALIASES`）。

**16. 强度报告说某条用例「杀不死任何变异体」，但它确实有用**
- 先分清是"断言弱"还是"用例多余"：该规则只有这一条用例且被杀不死 → 断言太粗，补「数值 / 边界两侧 / 动作结果」；同模块已有强用例 → 可合并。
- **兼容 / 性能 / 安全 / 易用**类用例默认豁免（`test_type` 命中即跳过"零贡献"判定），不要为它们硬补功能断言。

**17. 变异得分虚高，或某规则明显很弱却拿 100%**
- 几乎一定是 `killer_pattern` 写宽了（只锚功能名，如 `锁定` / `支付` / `登录`）。用 `--explain` 看命中原文，把 pattern 收窄到判别要素（`9\s*分钟`、`5000\s*元.{0,10}(及以下|免)`）。
- `DEL`（动作漏做）类最容易被功能名带过；需要更严时先 `--operators NUM,BND,NEG` 排除它再评估。
- 改完后必须重跑，且**不要拿不同 `--max-per-rule` / 不同 `mutants.json` 的两次得分做前后对比**（分母不同）。

**18. 第 11 项（需求密度）报了一大片，是不是阈值定高了**
- 先看分布：实测库常见"每个需求恰好 4 条"的平台化形态，模块级全绿但逐需求一卡就 44/47 不达标。**这是真实缺口，不是阈值问题**。
- 但阈值确实要分项目：复杂业务（多状态/多字段/多入口）用 6，单字段查看类用 4 甚至豁免。判据是**该需求里有几个可枚举的字段/状态/入口**，不是"别人写了几条"。
- 单纯为了过闸门把同一需求复制成 6 条薄壳 → 属形式拆分，会被冗余率红线挡回（≤8%），别这么干。

**19. 第 12 项（方法一致性）把正常用例判成"方法虚标"**
- 三个最常见的误判来源，先自查：
  1. **证据写在标题里**——标题含"边界值/不等于"但步骤预期没有断言。标题不算证据，这是故意的。
  2. **`0%` / `0 km/h` 这类下界**——脚本已把它算作边界字面量；若仍被判虚标，说明预期的数字被写成了文字（"零电量"），改成 `0%`。
  3. **等价类只写了 1 个取值**——这被判**「欠展开」**（告警，不算虚标）。要消掉它得按等价类矩阵补齐取值集合，不是删标签。
- 反过来：如果某条确实不该标边界值，**删标签比补假断言安全**——硬编一个"≥100 时提示"而需求里没有这个阈值，就是制造伪断言。

**20. 密度闸门打开后条数涨了，但抽检发现一半是凑数**
- 这正是"闸门单独用会逼出形式拆分"的典型症状。根因是**没有等价类矩阵做燃料**：一条需求只有 4 个真测试点，硬凑到 6 条只能复制。
- 处置顺序：先建矩阵（`equivalence_matrix.md`，Step 3.5）→ 再按矩阵行补用例（每行对应不同的类/边界点）→ 最后才调阈值。**反过来做一定失败。**

**21. 矩阵 lint 报「列数不足」或类别/预期读错位**
- 几乎一定是**每行少写了一列**（最常见是漏掉「类/边界点」）。Markdown 表格不会因少一列报错，只会把后面的列整体左移——所以 lint 用 L1b 硬拦。
- 自查两点：① 每行 `|` 分隔的单元格数要等于表头列数；②「取值域」填**完整合法域**（`0–100%`），「类/边界点」填**这一行的那一个点**（`0` / `100` / `-1`），两者别混。
- 若报「未消费等价类」一片红：那是真实缺口，不是 bug。先把用例补上再回填「用例 ID」——**不要填臆想编号**，`--cases` 会校验真实性。

**22. 矩阵 lint 说某字段「边界点仅 2 个」，但我确实写了 4 行**
- 检查这 4 行里有没有标 `[假设]`。`[假设]` 行**不计入**边界点数（否则编数据就能凑够 3 个，这道闸门就白设了）。
- 正确做法：先补数据字典/需求确认，把 `[假设]` 去掉再计入；确实无法确认时，保留 `[假设]` 并在报告里单列，接受该字段判不达标。

**23. 真实用例库跑出"零贡献 80%+"或"评估范围 0 条"**
- 先看表头：若同时有「顶级功能模块」与「功能模块」，早期版本会错取前者，导致整个 `设备端` 都被算进范围 → 已在 `coverage_audit.py` 修为**先精确匹配再包含匹配**；报这类问题时先确认版本。
- 「评估范围 0」= 用例没 `coverage_rule` 且需求侧 `module`（章节号）对不上用例 `功能模块`。两条路：给需求副本做 module 归一（临时），或给用例补 `coverage_rule`（长期）。
- 零贡献比例高不一定是"用例差"：若需求只覆盖模块里的一个子功能，范围内大部分用例本就不该杀死这些变异体 → 属于**范围粒度问题**，别据此删用例。

**24. `defect_audit.py` 报 `undecidable` 比例 > 30%，报告几乎全是"无法判定"**
- `undecidable` 只该吃掉两类：**(a)** 无效缺陷（被驳回/有意设计）；**(b)** 缺陷单信息不足（标题只有 `【V1】【APP】【训练】`，无现象描述）。
- 先看 (b) 再看 (a)：若某模块的缺陷集中在同一批不可测需求上，问题在**需求**（回推 `analysis_gate.md` H1），不是缺陷单烂。
- **不要**为了把数字做好看，硬把 `undecidable` 塞进 `escaped`——那会把逃逸率做成恐吓指标，两个月后没人再信这张表。

**25. 一个缺陷挂了 5 条用例，DDF 要不要加 5？——不要；另有"范围性用例"要单独排除**
- `DDF` 分子按**用例**去重（一条用例关联 5 个缺陷只算 1）；逃逸率的分母按**缺陷**去重（一个缺陷挂 5 条用例只算 1 个缺陷）。
- 另一个坑：一条用例关联 5 个缺陷，**不要**当成"高价值用例"奖励——它可能只是一条范围性用例（步骤含 `逐一/依次/分别`，一条覆盖 24 个子场景）。这类用例要按 `range_case` 排除在 DDF 排名之外，否则整个模块的发现力会被一条聚合用例顶满。
- 同理，模块级指标前必须先做归一：`设备端` / `横屏端` / `竖屏端` 这类端级标签不是功能模块，直接当模块会算出「横屏端 100% 逃逸」这种正确但没用的结论。

**26. 小样本库第 2/3 项过不了——整数粒度无解**
- 条数是整数，占比区间未必有整数解。默认 P0∈[10%,25%] 较宽、多数库有解，但**区间一收窄就会无解**：安全攸关项目常用的 P0∈[40%,45%]，在 **13 条的库上完全无解**（5 条=38.5%、6 条=46.2%，两端都出界）。
- 现在的处理：内置**整数粒度补偿**——仅当「该区间在该总条数下不存在任何整数解」时，按 `--ratio-tolerance`（默认 0.5 条）放宽，并在输出里显式打「整数粒度补偿」标记 + 追一条告警。
- 补偿**不豁免真实违规**：20 条库 0 条 P0 照样失败。想强制严格可 `--ratio-tolerance 0`。
- 若确实想让闸门严格生效，就把样本做大（≥20 条）或按项目实际调整 `--p0-min/--p0-max`，别去改用例优先级凑整数。

**27. `prescreen.py` 报 `TypeError: expected string or bytes-like object, got 'list'`**
- 原因：`steps` / `expected` 写成数组（`["第一步","第二步"]`），旧版 `norm()` 只吃字符串，在第 6 项（无语义重复）抛异常。
- **这个异常特别坑**：崩溃点在**第 6 项**，第 7~13 项全部不执行，而退出码仍是 `1` —— 看起来像"预审不通过"，实际是脚本挂了，打印里既没有 `=== 预审全部通过 ===` 也没有 `=== 预审不通过 ===`。
- 现已修（`norm()` 自动归一化 list）。**自查口诀**：输出里找不到「预审全部通过 / 需修正后重跑」任一行，就是崩溃，不是不达标 —— 去 `stderr` 找 Traceback。
- **配套契约**：崩溃现在固定 `exit 3`，不再与 `1`（不达标）混用。`exit 2` = 路径/参数错。**`1` 才要改用例，`2` 和 `3` 改用例都没用**。

**28. 第 14 项（范围性用例）把正常用例判成"一条吃掉 N 个场景"**
- 判据只看三件事同时成立：步骤含范围词（`逐一/依次/分别/遍历/全部/所有/每个/各个`…）**+** 并列对象 ≥3（`--range-min-objs`）**+** 预期只有 1 条断言。
- 三种常见误判与处置：
  1. **预期同构的批量校验**（如"N 个开关逐个拨动，都只验'状态应变为开'"）→ 在**备注列逐项展开**（`亮度=50 生效；音量=80 生效；…`）。第 14 项见此备注自动降级为提示，不阻断。
  2. **对象数被顿号高估**（"点击 设置、关于" 里"设置"和"关于"确实是 2 个对象，但业务上是一条路径）→ 调高 `--range-min-objs`，或忽略该条弱提示。
  3. **范围词出现在数据名里**（如按钮就叫"依次执行"）→ 属词表误伤，按项目加豁免说明，别去改用例。
- **它挡不住什么**：只认顿号/斜杠并列。一句话里塞 5 个动作用逗号连（"打开 A，点 B，再点 C"）切不出来——那类仍靠 `case_design.md` 第七节拆条判定表 + 人工评审。
