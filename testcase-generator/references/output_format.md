# 输出格式规范（Excel 15 列模板，v1.11.5 优秀库对齐）

Step 6 的强制主产物是 `.xlsx`，列定义如下。**打开即测试用例，无需二次整理。**

> 本文件只定义**列的容器与 JSON 字段映射**。每列"怎么写"（标题/前置/步骤/预期的写法与红线）见 `case_design.md` 四字段规范与 `naming_rules.md`，优先级口径见 `case_design.md` / `priority_p0_p3.md`，避免在此重复规定写法。

## 列定义（默认 15 列：管理 4 列 + 用例 8 列 + 执行与追溯 3 列）

| 序号 | 列名 | 说明 | 来源字段 | 是否必需 |
|---|---|---|---|---|
| 1 | **用例编号** | 自动生成 `TC-001` 顺序号；用例 JSON 含 `id` 时优先用 `id` | `id` 或自动 | 必需 |
| 2 | **顶级功能模块** | 一级分类（如 APP / 嵌入式固件 / 系统后台） | `top_module`（可选） | 可选 |
| 3 | **功能模块** | `/平台/模块` 路径 | `module` | 必需 |
| 4 | **设备型号** | 适用机型；通用用例缺省「公共」 | `device`（可选，缺省公共） | 可选 |
| 5 | **测试用例标题** | 精简 ≤30 字；命名红线见 `naming_rules.md` | `name` | 必需 |
| 6 | **测试优先级** | P0 / P1 / P2 / P3（四级，统一口径见 `priority_p0_p3.md`） | `priority` | 必需 |
| 7 | **测试类型** | **两族 17 类，不得自造**：功能族 = 模块功能测试 / 主流程测试 / 异常测试 / 边界测试 / 权限测试 / 兼容测试 / 性能测试 / 接口测试；UI 族 = 界面交互测试 / UI元素测试 / 文字查验测试 / 数据展示测试 / 用户体验测试 / 模块交互测试；跨族通用 = 功能测试 / 数据测试 / 等价类测试（预审 9c 强制校验，历史短写经别名归一） | `test_type` | 必需（缺省"功能测试"） |
| 8 | **APP版本类型** | 国内版本 / 国外版本 / `国内版本, 国外版本` | `app_version`（可选） | 可选 |
| 9 | **测试环境** | **公共复用**的编号式环境准备清单（双前置列做法 1：全库收敛为有限模板） | `environment`（可选） | 可选 |
| 10 | **前置条件** | 1. 2. 3. 编号，换行分隔（本条操作前的界面/状态，不与测试环境串味） | `precondition` | 必需 |
| 11 | **测试步骤** | 1. 2. 3. 编号，换行分隔 | `steps` | 必需 |
| 12 | **预期结果** | 与步骤一一对应，换行分隔 | `expected` | 必需 |
| 13 | **实际结果** | 执行阶段回填，生成时恒为空 | `actual` | 执行列 |
| 14 | **测试数据** | `键=值` 逐对换行 | `test_data` | 建议 |
| 15 | **备注** | 场景展开 / 来源与关联信息 | `remark`（可选） | 可选 |

> 第 1–12 列为测试用例的标准元素；第 13–15 列分别服务执行回填 / 数据外置 / 场景与来源备注。
> 「测试环境」与「前置条件」两列语义不得串味：可整块复制的环境准备进「测试环境」，本条界面/状态进「前置条件」（`excellent_case_patterns.md` 做法 1）。
> 旧 10 列（用例编号/测试模块/用例名称/优先级/测试类型/前置/步骤/预期/适用阶段/设计方法）用 `--legacy` 导出，兼容既有项目约定；`--with-environment / --with-remark` 仅在 legacy 模式下生效（15 列已内置）。

## 可选 11 列变体：双前置列（`--with-environment`）

按 `excellent_case_patterns.md` 做法 1（来源：真实优秀用例库 1278 条实证——`测试环境` 列 53 个模板值覆盖 1271 条，最大模板被 602 条共享），部分项目需要把"环境准备"与"本条界面状态"分成两列：

| 序号 | 列名 | 说明 | 来源字段 |
|---|---|---|---|
| 1–5 | 同 10 列 | 用例编号 / 测试模块 / 用例名称 / 优先级 / 测试类型 | 同 10 列 |
| **6** | **测试环境** | **公共复用**的编号式环境准备清单（如 `1.手机连接可用网络\n2.滑板车设备上电`），全库应收敛为有限模板 | `environment` |
| 7–11 | 同 10 列第 6–10 列 | 前置条件 / 测试步骤 / 预期结果 / 适用阶段 / 设计方法 | 同 10 列 |

- 生成命令：`python scripts/to_excel.py test_cases.json -o out.xlsx --with-environment`（模板同样支持：`--emit-template 模板.xlsx --with-environment`）。
- **两列语义不得串味**：环境准备（可整块复制）进「测试环境」，本条操作前的界面/状态（`已进入启动界面`）进「前置条件」。
- 默认仍输出 10 列，不影响既有项目约定。

## 可选 11 列变体：备注列（`--with-remark`）

用例库中存在**范围性用例**（一条用例需逐个构造/遍历多个并列子场景，步骤含 `逐一 / 逐个 / 依次 / 分别 / 遍历 / 逐项 / 逐条`）时，聚合式步骤无法直接照做，需在末列补「备注」承载**场景展开**：

| 序号 | 列名 | 说明 | 来源字段 |
|---|---|---|---|
| 1–10 | 同 10 列 | 用例编号 … 设计方法 | 同 10 列 |
| **11** | **备注** | 范围性用例的逐子场景操作展开；非范围性用例留空 | `remark` |

- 生成命令：`python scripts/to_excel.py test_cases.json -o out.xlsx --with-remark`（可与 `--with-environment` 叠加，此时为 12 列）。
- 备注推荐结构（三段式）：
  ```
  【场景展开·N 项】<总述：覆盖哪些类、共几项>
  1) <场景名>：<具体操作步骤> → <观测点>
  2) …
  【判定】<通过标准>
  ```
- 子场景清单必须**回到需求源表取**（枚举表、命令索引、参数阈值表），禁止臆造；本项目实践中 564 条命中 41 条（≈7%）。
- **不要为凑格式给非范围性用例编备注**——留空，保持备注列的信息密度。

## 可选第 12 列：关联缺陷（`--with-defect`）

版本收尾复盘（Step 6.5 缺陷反哺）后，把"这条用例实际拦过/关联了哪些真实缺陷"落在用例侧，便于回归选题与 DDF 统计：

| 序号 | 列名 | 说明 | 来源字段 |
|---|---|---|---|
| 1–10 | 同 10 列 | 用例编号 … 设计方法 | 同 10 列 |
| **11/12** | **关联缺陷** | 形如 `BUG-1234567（已修复）`，多条用 `；` 分隔；无关联留空 | `defect` |

- 生成命令：`python scripts/to_excel.py test_cases.json -o out.xlsx --with-defect`（可与 `--with-environment` / `--with-remark` 叠加，叠加后为 12 / 13 列，列序固定：环境 → … → 备注 → 关联缺陷）。
- **不加该参数时输出与 v1.7.x 完全一致（10 列，逐字节相同）**——主模板不因新能力而变，避免存量项目对不上表头。
- 只写**已确认关联**的缺陷：`defect_audit.py` 判为 `suspected` 的不写入（实测自动判「拦」人工一致率 0/5，写进列里等于给错误结论背书）。
- 缺陷号格式跟随项目（TAPD 长 id / 短号均可），但要保证与 `defect_map.json` 的 `id` 一一对得上，RTM 第三维才对得齐。

## 格式硬约束（Excel 容器相关，非写法）

- 前置条件、测试步骤、预期结果：使用**实际换行**，不是 `\n` 字符。
- **每步一行（强制，闸门 8b）**：`1. 2. 3.` 编号步骤一条一行——「1.输入密码2.点击登录按钮」这种同行挤多条属格式违规；优秀库 1278 条实测三字段零违规。括号内序数词（按钮1、按钮2）不算步骤编号。
- 测试步骤与预期结果严格一一对应（步骤数 = 预期数，写法详见 `case_design.md` 四字段规范）。
- 用例编号全局唯一、稳定（同一份 JSON 多次导出顺序一致）。
- 用例命名红线、优先级口径、预期可验证等**内容写法**见 `case_design.md` / `naming_rules.md`，不在此重复规定。

## 生成方式

```bash
# 由结构化用例 JSON 生成 xlsx（10 列）
python scripts/to_excel.py test_cases.json -o "test_output/v1.11 功能测试用例.xlsx"

# 仅生成空白模板（对照历史编写习惯）
python scripts/to_excel.py --emit-template "test-case-design/examples/testcases/模板.xlsx"
```

## 输入 JSON 字段（Step 5/6 结构化）

```json
{
  "cases": [
    {
      "id": "TC-001",
      "module": "登录",
      "name": "正确密码登录",
      "priority": "P0",
      "test_type": "功能测试",
      "precondition": "1. 用户已注册\n2. 网络正常",
      "steps": "1. 在登录页输入已注册手机号\n2. 输入正确密码\n3. 点击登录按钮",
      "expected": "1. 手机号输入框接受输入\n2. 密码输入框掩码显示\n3. 跳转至首页",
      "test_data": { "手机号": "13800138000", "密码": "Test@123" },
      "coverage_rule": "R-003",
      "design_method": ["场景法", "等价类划分"],
      "stage": "功能测试"
    }
  ]
}
```

> 说明：`id / test_type / stage` 为可选展示字段；`module / name / priority / precondition / steps / expected` 为必需；
> **标题字段规范名是 `name`**，`title` 作为历史别名被全链路（`prescreen` / `coverage_audit` / `to_excel`）同时接受，两者都给时以 `name` 为准。
> `steps` / `expected` 规范为「`1. 2. 3.` 换行分隔的字符串」，但写成数组（`["第一步","第二步"]`）也会被自动归一化，不会报错。
> `test_data / coverage_rule / design_method` 供质量预审（`prescreen.py`）与覆盖分析（`map_coverage.py`）使用；
> `defect`（可选，字符串）仅在 `--with-defect` 时导出。
