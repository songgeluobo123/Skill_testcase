# 测试用例四字段编写规范（标题 / 前置条件 / 测试步骤 / 预期结果）

> 适用于 `testcase-generator` 输出用例的「用例名称 / 前置条件 / 测试步骤 / 预期结果」四列。
> Step 5 生成**每条**用例时，强制按本节逐字段约束。命名红线另见 `references/naming_rules.md`，整体格式（编号、步骤=预期数）见 `references/case_design.md` 第 1、4、5、9、10 条。

---

## 一、用例标题

- **定位**：用简洁概括性语言体现**关注点与出发点**，使协作人员（执行人 / 评审 / 产品）快速理解意图，并判断测试点覆盖是否遗漏。
- **编写方式（任选其一）**：
  - 功能点：如 `网络正常时点击购买按钮弹出支付弹框`
  - 功能-流程：如 `会员购买页面-成功购买流程`
  - 状态或条件-结果：如 `无网状态-点击购买-提示无网`
- **与模块名结合**：格式为 `模块名-测试标题`，表示"在测试标题情况下测试该模块"。
- **锁定机制**：标题定下后即锁定用例中心点，前置条件、步骤、预期**均须围绕其展开**，不得发散。

## 二、前置条件

- **定义**：执行用例需满足的**条件或准备操作**（测试数据、角色权限、进入页面、展示弹框等）。
- **两大原则**：
  1. 条件本身**必须成立**；
  2. 该条件下，**后续步骤必能成立**（不再因前置缺失而中断）。
- **按需使用**：非所有用例都需前置条件，应在确认测试点后再判断是否必要。
- **确定方法**：列出"到达测试点"所需的全部步骤与预期，**保留关键步骤**，其之前的内容**归纳为前置条件**。
- **典型场景**：
  - 明确待测状态（如：已登录）；
  - 控制变量（除待测项外，其余已填 / 已就绪）；
  - 准备数据 / 页面 / 弹框；
  - 用例间关联（前置引用另一用例的预期结果）。
- **产出形态**：最终将条件**归纳为简洁结果**（不用冗长操作描述）。

## 三、测试步骤

- **定义**：验证测试点所需的**线性操作**——先做什么、后做什么。
- **描述要求**：清晰准确，**不出现假设性词语**；页面名、按钮名 / 位置须**明确**可定位。
- **围绕标题**：围绕标题展开，多余步骤**归入前置条件**。
- **禁止连词**：不出现「和 / 或 / 且」等连词，违者**拆分步骤**（一步一动作）或**拆分用例**。
- **不含预期**：不含预期结果内容，严格区分"步骤"与"预期"两列。

## 四、预期结果

- **定义**：完成步骤后程序的**表现**，即检查点。
- **围绕测试点**：围绕标题 / 测试点描述，**不有多余或遗漏**检查点。
- **不含步骤**：不含测试步骤（与步骤严格分离）。
- **数量下限**：每条用例**至少一**条预期结果。
- **检查点形态**：含界面表现、数据库数据、保存文件或其他**可验证表现**（不写"正确显示"，写具体内容 / 跳转动作）。

## 五、生成时字段联动自检（优化生成逻辑）

生成每条用例后，按以下链路逐字段核对，使四字段一致、不重不漏：

1. **标题锁定中心点** → 标题是否含预期判定词（R2）？是否 ≤20 字、无序号前缀、无【】、术语统一（见 `naming_rules.md`）？
2. **前置条件只放"标题成立前必须就绪"的内容** → 是否存在应在步骤里的操作被误放前置？条件是否自身成立且能支撑后续步骤？
3. **步骤是标题内待测操作的线性序列** → 是否含"和/或/且"（拆）？是否混入预期（移）？页面/按钮是否明确？
4. **预期逐步骤对应检查点（至少 1 条）** → 是否缺失？是否含步骤？是否可验证（界面/数据/文件）？

> 联动原则：**标题 → 前置 → 步骤 → 预期** 自上而下收敛，任一字段越界（步骤写成预期、预期写成步骤、前置含待测操作）均回退修正后再生成下一条。与 `case_design.md` 的"步骤数 = 预期数""单用例 ≤5 步"等约束一并生效。
