# 用例强度评审：需求层变异

> **状态**：`v1.7.0`，**默认 `--mut-gate p0`——P0 规则 <90% 或零强度即阻断**，P1–P3 只告警。
> 存量库摸底 / 灰度接入用 `--mut-gate warn`（只出报告）；阶段 3 才把预审第 7 项与 G3 启发式降级替换。
>
> **一句话**：覆盖回答"有没有人测"，强度回答"测得出错吗"。本文件定义后者。

---

## 一、为什么需要它（问题不在实现，在判据）

现有三道判据量的都是**字面**，不是**行为**：

| 判据 | 代码级实际口径 | 挡不住什么 |
|---|---|---|
| 预审第 7 项「预期可判定」 | 不可判定词黑名单 + `ASSERT_MARKERS`（`应\|必须\|需\|提示\|显示为\|\d`…） | 只要预期里有「应」或「提示」或任意数字就算过。「应提示账号已锁定」完全合规，却测不出阈值写错 |
| 覆盖率 / RTM | 有 `coverage_rule` **直接采信不二次校验**；无标注则 bigram Jaccard ≥ **0.08** | 阈值接近噪声 + 标注即算覆盖 ⇒ 用例挂在规则上就算覆盖，不管预期多弱 |
| G3 名义覆盖 | 启发式：`hit==1` 且规则文本跨度大 | 抓不到"2 条用例都很弱"（如 2 条用例全弱覆盖 1 条规则），也漏掉中等长度的规则 |

一份"预审 10 项全过 + 覆盖率 100% + 0 孤儿 + RTM 5 条全覆盖"的用例集，
实测变异得分只有 **21.1%**（4/19），3 条规则零强度，5 条用例零贡献。
这不是脚本 bug，是**代理指标的固有上限**：字面相似度无法证明"如果我写错了，你的用例会红"。

> 外部依据：Google *Code Coverage Best Practices*（覆盖率只证明被执行，不证明被正确检查，并推荐用 mutation testing 判断断言是否有效）；Barr et al.《The Oracle Problem in Software Testing: A Survey》(IEEE TSE 2015)；Molinelli et al. ASE 2025 实测"AI 生成的 oracle 变异得分 43% vs 人类 45%"，说明 oracle 才是瓶颈。

## 二、核心口径

| 概念 | 定义 | 与现有概念的关系 |
|---|---|---|
| **变异体（mutant）** | 对一条需求规则的**合理但错误**改版，如"锁定 10 分钟"→"锁定 9 分钟" | 类比代码变异，对象是规则文本，**不需要源码** |
| **有效变异体** | 非等价（语义确实不同）且**可黑盒观测**（界面/数据/日志能看出差异） | 等价变异体进 `mutants.ignore.json`，**不计入分母** |
| **杀死（killed）** | 用例集中至少 1 条用例的 **`expected`** 能区分该变异体与正确实现 | 与"覆盖"相反：覆盖看"有没有人挂上来"，杀死看"能不能分辨对错" |
| **变异得分** | `killed / valid_mutants` | 新增指标，替代 G3 的位置 |
| **零强度规则** | 变异得分 = 0：有覆盖，但一条错也测不出 | G1 的镜像（G1 = 没用例；零强度 = 有用例但白测） |
| **零贡献用例** | 杀死变异体数 = 0 的**功能类**用例 | 给了"删减/合并"一个客观依据；非功能类（兼容/性能/安全/易用）豁免 |
| **有效覆盖率** | `得分 ≥ 阈值 的规则数 / 规则总数` | 对外汇报时比"全局覆盖率"更可信的口径 |

### 两条硬规则

1. **只看 `expected`，不看 `steps`**。
   steps 里写"连续输错 5 次"是**操作**，不是**断言**。若把 steps 也算进匹配范围，弱用例会大面积假通过。
   需要对照时可显式加 `--match-scope expected+steps`，但结论应以默认 `expected` 为准。
2. **变异得分不能跨变异体集合比较**。
   得分 = 杀死数 / 变异体集合，而集合是本脚本生成的——换个 `--max-per-rule` 或换一批 `--semantic` 变异体，分母就变了。
   **只有"同一份 `mutants` 集合下的前后对比"才有意义**（例如补用例前 21.1% → 补后 68.4%）。

## 三、变异算子库

### 3.1 确定性算子（脚本自动抽取，无模型调用）

| 算子 | 代号 | 改法 | 抽取依据 | 每规则配额 |
|---|---|---|---|---|
| 逐字文案 | `TEXT` | 「打开麦克风与摄像头」→ 改成别的文案 / 错字 / 漏句 | 规则里被引号包住的固定文案（`"…"` / `「…」` / `“…”`） | 2 |
| 边界方向 | `BND` | 「超过 5000 元」→「5000 元及以上也需验证」 | 比较词表（超过/大于/以上/以下/不超过/不少于/至少/最多…）+ 邻近数值 | 2 |
| 数值 | `NUM` | 5 次→4 次；10 分钟→9 分钟；800ms→799ms；5s→4s | 数字 + 单位（次/分钟/秒/毫秒/天/元/字符/%/个/条/人/步/ms/s/min/kg/km·h⁻¹…） | 2 |
| 否定翻转 | `NEG` | 「不可复用」→「可复用」；「免验证」→「需验证」 | 否定词表（不可/不能/不允许/禁止/不得/无法/无需/不支持/免）+ 后续 1–6 字 | 1 |
| 动作删除 | `DEL` | 「释放库存」动作漏做；「回跳」漏做；「截断」漏做 | 动作词表（关闭/释放/回跳/截断/清零/置灰/隐藏/锁定/重置/拒绝/删除/回滚） | 1 |
| 枚举 | `ENUM` | 「返回热门搜索」→「返回空」；并列项 A、B 漏掉 B | 返回/展示/显示 + 默认/热门/推荐/全部；顿号并列 | 1 |

> `TEXT` 为什么单列在最前：**文案类规则只有"改一个字/换一句"这一种真实错法**，而这类规则在真实库里占比很高（AI Coach 实测 35 条规则中有 9 条属文案或模板类）。没有这个算子，它们会被误判成"不可测量"，把需求缺陷误报成工具缺陷。
> `NUM` 的英文单位后面带 `(?![A-Za-z])` 负向前瞻——否则 `10 steps` 会被切成 `10 s` 造出一个无意义的变异体。

**排序与配额的两条设计取舍（都是踩过坑才定的）**：

- **先保多样性，再谈数量**。若只按总量截断，一条含两个数字的规则会被 4 个 `NUM` 变异体占满，"否定翻转/动作漏做"根本不生成——等于自己把检出能力砍掉一半。
- **`NUM` 的 `-1` 侧整体排在 `+1` 侧之前**。差一（少算一次、少锁一分钟）是最常见的实现错误，也对应 Guru99 强调的"分别检验每个极限的两侧"。

### 3.2 语义算子（需显式 `--semantic`，默认关）

| 算子 | 代号 | 改法 | 为什么必须靠语义 |
|---|---|---|---|
| 顺序交换 | `ORD` | 「先校验后提交」→「先提交后校验」 | 需要理解因果顺序 |
| 状态迁移 | `STM` | 状态机少一条迁移边 / 迁移目标写错 | 需要还原状态图 |
| 幂等 | `IDEM` | 允许重复提交 / 重复扣款 / 重复领券 | 需要理解"只一次"的业务含义 |

用法：先让模型按 `{rule_id, operator, wrong_claim, killer_pattern}` 产出 `mutants.json`，**落盘并纳入版本管理**，再随脚本跑。落盘的理由：同一规则两次生成结果不同会导致得分不可复现，评审必须对着固定文件跑。

```json
[
  {"rule_id": "R-103", "operator": "ORD",
   "wrong_claim": "先跳登录页、登录成功后才记录原访问地址（导致回跳丢失）",
   "killer_pattern": "回跳|返回原访问地址|回到.{0,8}详情"}
]
```

## 四、`killer_pattern` 规范（本能力唯一的正确性要害）

**规则**：pattern 只能锚定「**能区分正确与错误的那一个要素**」——数值 / 边界方向 / 枚举项 / 动作结果 / 否定词；**不得只锚定功能名**。

| 场景 | ✅ 正确 | ❌ 错误 | 错在哪 |
|---|---|---|---|
| 10 分钟 → 9 分钟 | `9\s*分钟` | `锁定` | 只锚功能名，任何写了"锁定"的弱用例都会被算成"杀死"，得分虚高 |
| 5000 元边界翻转 | `5000\s*元.{0,10}(及以下\|免\|不需要)` | `支付` | 同上 |
| 不回跳原地址 | `回跳\|返回原\|原访问地址` | `登录` | 同上 |
| 旧验证码可复用 | `(?:不可\|不能\|无法\|禁止)复用` | `验证码` | 同上 |

**自检手段**：`--explain` 逐条打印 `pattern` 与命中的用例原文。任何一条"被标注 killed 但我看不出它怎么区分对错"的，就说明 pattern 写宽了——这是最容易出的错，也是比"不度量"更危险的地方（虚高的分数会让人放心）。

**反例回归**：`test_mutation_audit.py` 里固定了两条断言——
① 弱预期（`应提示账号已锁定`，无时长）必须判 `survive`；
② 强预期（`第 4 次输错后应仍停留在登录页且不出现锁定提示`）必须判 `killed`。
任何改动若让 ① 变 killed，说明 pattern 或被匹配文本被放宽了，直接判失败。

## 五、命令

```bash
# 默认：P0 规则 <90% 或零强度即阻断（退出码 1），P1–P3 只告警
python scripts/mutation_audit.py test_cases.json requirements.json -o 强度报告.md

# 存库摸底 / 灰度接入：只出报告，不阻断
python scripts/mutation_audit.py test_cases.json requirements.json --mut-gate warn

# 收紧：全量阻断（任何规则不达标都返回 1）
python scripts/mutation_audit.py test_cases.json requirements.json \
    --mut-min 0.70 --p0-mut-min 0.95 --rule-floor-block 0 --mut-gate block

# 语义变异体 + 等价白名单
python scripts/mutation_audit.py test_cases.json requirements.json \
    --semantic mutants.json --ignore mutants.ignore.json

# 只查某条规则 / 只用部分算子 / 输出 JSON 给流水线
python scripts/mutation_audit.py test_cases.json requirements.json --explain --rule R-101
python scripts/mutation_audit.py test_cases.json requirements.json --operators NUM,BND
python scripts/mutation_audit.py test_cases.json requirements.json --format json -o audit.json
```

退出码：`0` 放行（`warn`/`off`，或 `p0` 模式下无 P0 不达标）· `1` 阻断 · `2` 输入/参数错误。

### 参数速查

| 参数 | 默认 | 说明 |
|---|---|---|
| `--mut-min` | `0.70` | 全局变异得分达标线 |
| `--p0-mut-min` | `0.90` | P0 规则达标线（P0 一票否决，故更高） |
| `--rule-floor-block` | `0.0` | 单规则得分 ≤ 该值判零强度 |
| `--mut-gate` | `p0` | `p0` 只卡 P0（当前默认）/ `warn` 只告警 / `block` 全量阻断 / `off` 不判定 |
| `--max-per-rule` | `6` | 每规则变异体上限（仍受算子配额约束） |
| `--match-scope` | `expected` | 杀死判定文本范围 |
| `--operators` | 全部确定性算子 | 只用指定算子，逗号分隔 |
| `--semantic` / `--ignore` | 无 | 语义变异体 / 等价白名单 |

## 六、报告结构与怎么用

```
# 用例强度评审报告（需求层变异）
一、总览                    模块 × 变异体 × 杀死 × 得分 × 零强度数
二、零强度规则（最高优先级）  逐条列存活变异体 + "要杀死它，预期必须具备什么"
三、弱覆盖规则（得分 < 阈值）
四、零贡献用例              可补断言 / 可合并
四·五、映射缺口             能测出错但没挂 coverage_rule 的用例
五、不可测量规则            抽不出变异体 → 多半是需求本身不可测
六、结论                    达标与否 + 回填优先级
```

**回填优先级（不要平摊工作量）**：
`零强度规则` → `P0 弱覆盖` → `其余弱覆盖` → `零贡献用例`。

**补的是"断言要素"，不是"条数"**。绝大多数情况下不需要新增用例——把已有用例的预期从功能级下沉到要素级即可（见下例）。这也解释了为什么本能力和"用例数量膨胀"没有关系。

| 规则 | 弱预期（当前） | 强预期（改造后） |
|---|---|---|
| 锁定 5 次 / 10 分钟 | 「应提示账号已锁定」 | 「第 4 次输错后应仍停留在登录页且不出现锁定提示」+「锁定后第 9 分钟登录应仍提示已锁定，第 11 分钟应可正常进入」 |
| 超时 15 分钟 | 「应提示订单已关闭」 | 「提交后第 14 分钟支付应成功；第 16 分钟支付应提示订单已关闭，且库存应恢复为 10」 |

**"不可测量规则"是需求缺陷信号**：规则里既没有数值、也没有边界方向/否定/可观测动作（典型："体验流畅""交互友好"），说明它本身不可测。回推 `analysis_gate.md` 的 H1（禁止假设），先改需求，不要硬写用例。

## 七、阻断范围与上线节奏

| 阶段 | 版本 | 阻断策略 | 状态 |
|---|---|---|---|
| 1 只读灰度 | `v1.6.0` | `--mut-gate warn`，只出报告 | ✅ 已完成，基线见第六节 |
| **2 P0 阻断** | **`v1.7.0`** | **默认 `p0`：P0 规则 <90% 或零强度即阻断；P1–P3 告警** | ✅ **当前** |
| 3 替换弱启发式 | `v2.0.0` | `block` 可配；第 7 项降快筛、G3 由变异得分取代 | ⏳ 待定 |

**为什么只卡 P0（而不是全量阻断）**
- P0 是一票否决的主流程 / 安全项，允许它"看起来测了其实测不出错"，等于把发布门禁建在文字上；
- 存量库的 P1–P3 普遍偏弱（实测全库基线 63.1%），立刻全量阻断会造出成片红灯，团队只会去关闸门；
- `block` 保留给"新写模块"或强合规场景，按项目在检查点①开。

**阈值怎么定（不要拍脑袋）**：先拿真实用例库跑一次 `warn` 摸底。
- 基线 < 40% ⇒ 全库普遍弱，起步线定 `0.45`，先消灭零强度规则，再谈整体分；
- 基线 ≥ 70% ⇒ 直接按 `0.70 / 0.90` 卡。
- **P0 线建议不动**：`--p0-mut-min 0.90` 是"允许 10% 的可错空间"，再低就失去闸门意义；若某 P0 规则确实无法测（不可测量），走检查点②说明并登记风险，而不是调低阈值。

**自检基线（本仓库 fixture）**：`skill_research/_exp/` 的 8 条用例 + 6 条规则 → 有效变异体 19，杀死 4，**21.1%**；零强度规则 3 条（R-102 / R-103 / R-201）；零贡献用例 5 条。
同一套用例在外围手写 19 个变异体（含 steps 匹配）时测得 **26.3%** —— 两个数不同是正常的（变异体集合与匹配范围都变了），**印证第六节"不可跨集合比较"**。对外只报同一集合下的前后对比。

> **一个真实的修复记录（值得记住）**：`DEL` 的 `锁定` 最初写成 `锁定|冻结|封禁`，于是"应提示账号已锁定"这种**只验证提示文案**的用例也被判"杀死"。但提示弹出 ≠ 锁定生效（吞掉锁动作、只弹提示是经典缺陷），这就是假杀死。改成结果态 `(?:仍|继续|依旧|再次).{0,10}(锁定|无法登录)|锁定(?:中|状态|生效)` 之后，该用例被正确判为**零贡献**。
> 结论：**动作类的 killer 必须是"结果态"，不能是动作名本身**。`test_mutation_audit.py` 的 B1 断言就是为这类回归设的。

## 八、已知局限（用之前先知道）

1. **等价变异体无法自动判定**。数学上等价判定不可判定；本脚本只能靠 `--ignore` 白名单 + 人工确认。Meta 的实测参考：LLM 等价检测精确率 0.79 / 召回 0.47，加静态预处理后 0.95 / 0.96 —— 所以**先人工过一遍白名单再定阈值**。
2. **`DEL` 类变异体最弱**。"动作漏做"的观测点极易写成功能名（提示文案），已按"killer 必须是结果态"收紧（见第六节修复记录），但它仍是最弱一类。需要更严的评估时用 `--operators NUM,BND,NEG` 先排除它。
3. **规则文本质量决定上限**。规则里没有数字/否定/动作词 ⇒ 抽不出变异体 ⇒ 进"不可测量规则"。这不是脚本缺陷，是需求侧信号。
4. **语义类（ORD/STM/IDEM）默认关**。开了之后得分依赖 `mutants.json` 的版本，必须随项目落盘管理。
5. **不替代执行**。它度量的是"用例写得够不够锋利"，不是"跑起来会不会失败"（后者要靠执行环境与真实实现）。
6. **「零贡献用例」只在评估范围内统计**。范围 = 挂了被评审规则的用例 + 模块名能对上的用例。若需求侧 `module` 是章节号（如 `. 播报优先级`）而与用例模块（如 `登录`/`训练`）对不上、用例又没有 `coverage_rule`，范围会是 0，第四节自动跳过并提示先补映射。**这是真实库最常见的落地阻碍，先补 `coverage_rule` 再谈强度。**
7. **模板类规则会判零强度，这不是误报**。含 `{速度}` 占位符的话术模板能生成 `TEXT` 变异体，但用例通常只校验"播了没播"而不逐字比对模板字面——说明该规则确实没被逐字验证，属真实缺口。

## 九、与其它闸门的边界

| 闸门 | 管什么 | 本文件的边界 |
|---|---|---|
| 分析闸门（Step 1） | 方向对不对、需求读懂没有 | 不管方向；只判"已确认的需求"被测得够不够锋利 |
