# 缺陷反哺评审（Defect Loop）— 用真实缺陷找漏

> 第六道闸门 · 事后复盘 · **默认不阻断**。命令：`scripts/defect_audit.py`。配套自测：`scripts/selftest_defect.py`。

前面几道闸门（分析 / 矩阵 / 预审 / 强度 / 评分 / 覆盖）量的都是「我们假想的错」：
预审第 7 项是词表黑名单、覆盖率对显式 `coverage_rule` 直接采信、变异体是脚本自己造的。
三者可以**集体及格、又集体错过同一个真实故障**——因为没有任何一个环节引入外部事实。

本能力把「真实发生过的缺陷」作为地面真值，回答一个前面几道闸门都回答不了的问题：
**这条缺陷发生的时候，我们的用例库为什么没变红？**

---

## 一、能力边界（先说不能做什么，这是本能力的要害）

| 能可靠回答 | 不能可靠回答 |
|---|---|
| 这条缺陷**漏了**（库内找不到能拦它的断言 → `escaped`） | 这条缺陷**被拦住了**（`prevented`） |
| 漏的是**哪一类断言**（数值 / 逐字文案 / 结果态 / 唯一性 / 否定 / 边界 / 现象） | 具体是哪条用例拦的（只能给候选） |
| 哪些模块**一条用例都没有**却有事故（零覆盖 + 有事故） | 拦截率 DER（除非缺陷单有「发现阶段」字段） |

**实测依据**（225 条真实缺陷 × 2,431 条真实用例，2026-11）：

- `escaped` 抽检 10 条中 5 条，人工复核 **5/5 成立**；
- `suspected`（疑似已拦）抽检 5 条，人工复核 **0/5 成立**。

`suspected` 的典型误判：

| 缺陷 | 被判「疑似已拦」的用例预期 | 为什么不算拦 |
|---|---|---|
| 训练完成后弹出「训练执行出错」弹窗 | 记录生成完成后自动跳转至完成界面 | 跳转成立 ≠ 没有错误弹窗，两者可同时存在 |
| 辅助器材只能单选 | 节奏与方向界面「3.3 仅能单选」 | 是另一个控件，选的不是同一件事 |
| 网络断开发送验证码刷出**两个**提示 | 弹出提示，网络已断开 | 断言了"有提示"，没断言"只一个" |
| 用户校验界面邮箱账号应无法点击修改 | 邮箱、「重置密码」按钮正确显示 | 只断言显示，不断言只读 |

根因不是阈值：`mutation_audit` 能做「杀死判定」，是因为变异体与用例出自**同一句需求**，语义天然对齐；
缺陷与用例是**两份独立文本**，命中同一个动作词（跳转/选中/弹出/重置）并不等于验的是同一件事。

> 所以默认口径：**「漏」自动判，「拦」只给候选、不宣称**。把 `suspected` 当 `prevented` 上报，
> 就是制造第二个「假覆盖率」。若确实需要自动判「拦」，前置条件是「需求规则 ID ↔ 用例 `coverage_rule`」
> 的显式映射（见第九节），当前用例库普遍为空。

## 二、四态口径（判决的唯一权威定义）

| 状态 | 定义 | 计入分母 | 可信度 |
|---|---|---|---|
| `escaped` 逃逸 | 缺陷确实发生，且库内没有任何 `expected` 能拦住它 | ✅ | **可靠**（"漏"是事实） |
| `undecidable` 不可判定 | 无效缺陷（被驳回 / 有意设计）或信息不足（标题只有标签、无现象描述） | ❌ | — |
| `suspected` 疑似已拦 | 缺陷标题里的判别要素在某条关联用例 `expected` 的**同一分句**里出现过 | ✅（算未确认逃逸） | **不可信，需人工逐条确认**；默认不进报告 |
| `prevented` 已拦 | 仅 `--prevented-mode auto` 时把 `suspected` 直接采纳 | ✅ | **慎用**，会把漏测洗成拦截 |

判定顺序：无效缺陷 → 信息不足 → 显式关联（L1）→ 结构匹配（L2）→ 在候选里找强判别要素。

**强判别要素**（只有它们能触发 `suspected`，且**只在 `expected` 里找**，不看标题、不看步骤）：

- `NUM` 数值：须带单位/百分号、是小数、或 ≥2 位整数（`【V1】` 的 `1` 不算）
- `TXT` 逐字文案：引号内原文（支持 `"…"` `'…'` `「…」`）
- `ACT` 结果态动作：跳转/弹出/置灰/清空/停止/选中/保存…
- `UNIQ` 唯一性/计数：仅一条 / 只能 / 同一…

`NEG`（不/无/未）与 `BND`（超过/至少）是**弱要素**：它们到处都是，单独命中不算拦住，只用于归因缺口类型。

**同分句约束**：判别要素与「对象词」必须落在 `expected` 的同一个分句里。不切分句的话，
`expected` 里任意位置的「跳转」都会跟标题里的「跳转」撞上——这是最大的一类假拦截来源。

## 三、指标怎么读

| 指标 | 公式 | 读法 | 何时不可算 |
|---|---|---|---|
| 缺陷逃逸率 | `escaped / (总缺陷 − undecidable)` | **越低越好**；下界即「已确认漏」 | 总能算 |
| 真实逃逸区间 | `escape_rate ~ (escaped+suspected)/evaluable` | 上界 = 疑似也算漏 | 总能算 |
| DDF 用例缺陷发现力 | 有关联缺陷的用例数 / 有效用例数 | 越高越好；分子按**用例**去重 | 总能算 |
| DER 缺陷拦截率 | 测试发现 /（测试发现 + 线上发现） | 越高越好 | **缺「发现阶段」字段时不可算** |
| 回归缺陷率 | `regression_number ≠ 0` 的缺陷 / 有效缺陷 | "改好又坏"的比例 = 验证不足的硬信号 | 总能算 |
| 不可判定率 | `undecidable / 总缺陷` | 缺陷单质量的反向指标 | 总能算 |

**DER 的红线**：本项目零线上缺陷、但缺陷单「发现阶段」字段全空时，**不要**倒推出 100% 拦截率。
分子分母都拿不到就不算，报告写"不可算"并列出所需字段——把一个算不出的指标填成满分，
是最容易被戳穿的那种自嗨。

**区间而不是点估计**：`suspected` 未确认，所以逃逸率天然是一个区间。汇报时给区间（如
「69.2% ~ 100%」），别只给下界当结论。

## 四、命令与产物

```bash
# 层 1：只吃缺陷单（零映射成本，先看数据能不能用）
python scripts/defect_audit.py bugs.json --layer 1 -o 缺陷体检.md

# 层 2：+ 用例库 → 四态判定 / DDF / 死用例候选
python scripts/defect_audit.py bugs.json cases.xlsx \
  --module-map module_map.json --layer 2 -o 缺陷反哺报告.md \
  --emit-map defect_map.json --emit-backfill regression_backfill.json

# 层 3：+ 回填草案（每个逃逸缺陷缺哪类断言、挂到哪条用例）
python scripts/defect_audit.py bugs.json cases.xlsx \
  --module-map module_map.json --layer 3 -o 缺陷反哺报告.md
```

| 参数 | 说明 |
|---|---|
| `bugs` | `.json`（TAPD dump `{data:[{Bug:{}}]}` / 扁平数组）/ `.xlsx` / `.csv` |
| `cases`（可选） | 层 2 起必填；`.xlsx` 直读存量用例库，`.json` 读 `test_cases.json` |
| `--layer {1,2,3}` | 默认 1 |
| `--module-map` | 模块归一副本 `{"缺陷模块":"用例模块"}`；映射为 `""`＝库内零覆盖 |
| `--gate {off,warn}` | **默认 `off` 恒放行**；`warn` 逃逸率超 `--escaped-warn`（默认 0.80）只告警 |
| `--prevented-mode {off,auto}` | 默认 `off`（`suspected` 不采纳为 `prevented`） |
| `--with-suspected` | 在报告里输出疑似清单（默认不输出：确认率 0/5，噪声为主） |
| `--emit-map` / `--emit-backfill` | 输出 `defect_map.json`（数据契约）/ `regression_backfill.json`（回填草案） |
| `--l2-min-keywords` / `--l3-threshold` | L2 关键词命中数（默认 2）/ L3 相似度（默认 0.35，0 关闭） |
| `--protected` | 变异审计的 killer 用例名单，死用例候选会跳过 |

产物：`缺陷反哺报告.md`（六节：数据体检 / 全局指标 / 模块分布 / 四态明细+缺口分组 / 回填草案 / 结论）、
`defect_map.json`、`regression_backfill.json`。

## 五、缺口分类与回填顺序

逃逸缺陷按「缺哪类断言」分组，直接对应回填动作：

| 缺口 | 含义 | 回填动作 |
|---|---|---|
| `NUM` | 缺具体数值 | 补逐数/逐值断言，不能只写"显示正确" |
| `TXT` | 缺逐字文案 | 补引号内原文，不能只写"提示正确" |
| `ACT` | 缺结果态证据 | 补状态变更后的可观测现象，不能只写"提示已XX" |
| `UNIQ` | 缺唯一性/计数 | 补"仅一条""同一"类断言 |
| `NEG` | 缺显式否定结果 | 补"不出现/不再弹出/无新增" |
| `BND` | 缺边界两侧 | 未达 / 已达各一条 |
| `PHEN` | 缺陷本身没写"错成什么样" | **先回推需求**（`analysis_gate.md` H1），不是补用例 |

**回填顺序**（与 `mutation_review.md` 同构）：

1. 零覆盖模块（库内一条用例都没有）→ 这是真缺口，要新建用例；
2. `NUM` / `TXT` / `ACT` 缺口 → **优先在已有用例的 `expected` 里补断言，通常不需要新增用例**；
3. `NEG` / `BND` → 补反向与边界两侧；
4. `PHEN` → 退回需求侧，写清"错成什么样"再谈用例。

**一条铁律**：补断言优先于补用例。真实库里 128 条逃逸缺陷，绝大多数对应的是
「用例已存在但预期写成了"正常显示"」，而不是「这个场景没人测」。

## 六、数据前置（不满足就别硬算）

| 想要的结果 | 必需数据 | 当前实测 |
|---|---|---|
| 四态判定 / 逃逸率 / DDF | 缺陷标题 + 模块 + 用例库（`功能模块` + `用例名称` + `预期结果`） | ✅ 可用 |
| 模块级下钻 | 缺陷模块 → 用例模块的归一映射（`--module-map`） | 需人工建一次（约 30 条） |
| `DER` | 缺陷单「发现阶段 / 来源」字段 | ❌ 0% 填充 |
| 死用例候选池 | 用例库「测试结果」列 | ❌ 0% 填充 |
| 自动判「拦」 | 需求规则 ID ↔ 用例 `coverage_rule` | ❌ 基本为空 |

**死用例候选池的执行率门槛**：`测试结果` 填充率 <10% 时**直接不出候选池**。
全空时"从未失败"和"从未跑过"无法区分，强行出池会把 80% 的库判死——宁缺勿滥。

## 七、常见坑（都踩过，都写进了断言）

1. **版本号当判别数值**：`【V1】` 里的 `1` 几乎必然在任意 `expected` 里命中 → 必须 `strip_tags()` 再去抽数值，且数值要满足「带单位/小数/≥2 位」。
2. **TAPD 富文本的 CSS 数字**：`description` 里的 `font-size: 18px`、`color: #34383e` 会抽出 `18`/`50` → 必须先 `strip_html()`（去 script/style、HTML 标签、CSS 声明、URL、实体）。
3. **模块内泛动词命中即判拦**：候选池限 `top=3`、关键词过 `STOP_KW`（正常/显示/提示/页面/界面…）、再加同分句约束。
4. **中文直角引号抽不出文案**：`「训练完成」` 这种写法在产出规范里很常见，引号字符集必须含 `「」`。
5. **「发现阶段全空」误报**：若脚本先归一字段再读，读原始字段名会永远判空 → 归一后要读 `phase`。
6. **判决不可复现**：用 `set` 取前 N 个关键词，顺序受 hash 影响 → 按「长度降序 + 字典序」取，保证两次跑结果一致。
7. **分页导出重复计数**：同一缺陷 id 出现在两页 → 按 id 去重，否则分母被抬高。
8. **端/形态级标签被当功能模块**：`设备端` `移动端` `横屏端` `竖屏端` 不是模块，直接当模块会得到「横屏端 100% 逃逸」这种正确但没用的结论 → 归一到第三段标签（训练/首页/引导）后再统计。
9. **信息不足判定失效**：若写成「标题短 **且** 无标签」才算信息不足，几乎永不触发（缺陷都有标签）→ 改成「剥离标签后 < 4 字」。
10. **零覆盖模块塌成"未分模块"**：映射为 `""` 时不要置空名字，保留并标「（库内无对应模块）」，否则"哪块完全没测"这条最有价值的结论会被抹掉。

## 八、与既有闸门的关系

```
                 外部事实：TAPD 缺陷单（历史 / 本版本）
                              │  Step 6.5 缺陷反哺
                              ▼
①分析 ──▶ ②预审 ──▶ ③强度 ──▶ ④评分 ──▶ ⑤覆盖 ──▶ ⑥缺陷
STOP&ASK   10 项     变异 P0阻断   ≥90      G1-G3     逃逸率/DDF/缺口
                              │
                              └── 缺陷模式回灌 Step 3 测试点（下次设计的必答项）
```

- **新闸门放最后、默认不阻断**。前五道是"出口检查"，第六道是"事后复盘"；
  把它做成阻断项会直接卡死存量项目（2,431 条库里 0 条有缺陷关联，一上来必然 100% 逃逸）。
- 与 ⑤ 覆盖的关系：⑤ 的 G1/G2/G3 看"需求有没有用例"，⑥ 的 G4（逃逸缺口）看"用例有没有拦住真实故障"；前者是内部一致性，后者是外部事实。
- 与 ③ 强度的关系：③ 造变异体证明"能测出错"，⑥ 用真实故障证明"确实没测出错过"，一正一反。

## 九、已知局限与后续

| 局限 | 影响 | 解除条件 |
|---|---|---|
| 不能自动判「拦」 | 无法给出拦截率点估计，只能给逃逸率区间 | 需求规则 ID ↔ `coverage_rule` 显式映射 |
| 模块归一靠人工映射 | 映射缺失时模块级指标会糊成"未分模块"/端级桶 | 建一次 `--module-map`（30 条左右），后续可复用 |
| 只做"文本可拦截性"判定 | 测「不替代执行」——用例写了正确断言但执行时没跑，本能力看不出来 | 接入执行记录（用例「测试结果」列） |
| 缺陷单质量决定上限 | 标题只有 `【V1】`、无现象描述的缺陷判 `undecidable` | 缺陷单模板强制"现象 + 复现路径" |

**后续优先级**：先补 `coverage_rule` 锚点（解锁"拦"的自动判定）→ 再接执行记录（解锁死用例池）→
最后才谈 DER（需缺陷单加「发现阶段」字段，属流程改造，不是脚本能解决的）。
