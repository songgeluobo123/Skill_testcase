# 功能点定义（强制）

> **核心原则：功能点 ≠ 需求点。** 功能点不是直接复制 XMind / PRD 里的需求描述，
> 而是把需求拆解成"可独立测试的最小单元"。

---

## 一、功能点的判断标准（同时满足）

| 维度 | 说明 |
|---|---|
| 可观测 | 有明确的输入 / 输出或状态变化 |
| 可测试 | 可以设计测试用例来验证 |
| 原子性 | 不可再分的最小可测单元 |
| 业务价值 | 对用户有明确的业务意义 |

只满足其中一两项的，通常是"需求描述"而非"功能点"，需要继续拆解。

## 二、功能点分类（按交互模式）

| 类别 | 典型载体 |
|---|---|
| 数据展示类 | 列表页、详情页、仪表板 / 数据看板 |
| 数据操作类 | 表单页（新增 / 编辑 / 搜索）、批量操作、导入 / 导出 |
| 流程类 | 向导 / 多步骤流程、审批 / 工作流 |
| 交互类 | 搜索、筛选 / 过滤、排序 |
| 系统功能类 | 用户账户管理、权限 / 角色管理、系统配置 |
| 特殊功能类 | 文件管理、消息 / 通知、支付功能 |

## 三、功能点梳理原则

- **以页面 / 二级页为单位**：每个功能子模块的页面、二级页为单位梳理功能。
- **功能类型**：列表展示、搜索、新增、编辑、详情、删除、导入导出、筛选、排序等。
- **示例**：
  - 需求原文："用户可以在订单中心管理自己的订单" → 拆为功能点：订单列表展示、订单搜索、订单筛选、订单详情查看、订单取消（每个都是原子可测单元）。

## 四、功能点 → 测试点的衔接

- 每个功能点在 Step 3 至少产出一组测试点（正向 / 输入域 / 业务规则 / 异常）。
- 功能点清单应随需求树层级组织，便于后续在 XMind / Excel 里按模块归类，避免"每个功能点单独建目录"导致目录爆炸。
