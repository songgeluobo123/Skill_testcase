# 用例覆盖率评审（逆向评审）

本文件定义 `testcase-generator` 的**逆向能力**：不是"从需求生成用例"，而是"拿已有用例库回审需求"——回答"哪个模块漏得最多、缺什么类型的用例"。

> 与正向流程的关系：正向（Step 1–6）产用例；逆向（本文件）验用例。两者共用同一份 `requirements.json`。
> 与 `quality_prescreen.md` 的边界：预审是**全局**闸门（总覆盖率、占比、写法合规）；本文件是**模块级下钻**，专治"全局 95% 掩盖某模块 40%"。

---

## 一、两个使用时机

| 时机 | 输入 | 目的 |
|---|---|---|
| **A. 生成后自审**（Step 6 之后可选） | 刚生成的 `test_cases.json` + `requirements.json` | 交付前确认没有模块被"整体漏掉" |
| **B. 存量用例库评审**（接手项目 / 版本回归前） | 历史 `.xlsx` 用例库 + 需求文档抽出的 `requirements.json` | 找出老用例的覆盖空洞，作为补充依据 |

> 存量库通常**没有** `coverage_rule` 字段，脚本会自动做文本匹配（见第三节），无需先补标注。

---

## 二、三项核心能力

### 1. 多格式输入解析

- **用例**：`.json`（数组或 `{"cases":[...]}`）或 `.xlsx`（自动识别中文表头：用例编号 / 测试模块 / 用例名称 / 优先级 / 测试类型 / 前置条件 / 测试步骤 / 预期结果）。
- **需求**：`requirements.json`（`scripts/extract_requirements.py` 产出：`[{id, module, text, type}]`，只评审 `included`）。

### 2. 模块级覆盖率

```
模块覆盖率 = 该模块已覆盖的需求规则数 / 该模块需求规则总数 × 100%
```

- 达标阈值默认 **70%**（`--module-min`），低于即列为「重点补充对象」。
- 覆盖率**只计强匹配**（显式 `coverage_rule` 或文本相似度达标）；仅模块名相同算**疑似覆盖**，单列待人工确认，不抬高覆盖率。

### 3. 缺口自动识别（三类 + 一类外部缺口）

| 代号 | 缺口 | 判定口径 | 危害 | 由谁算 |
|---|---|---|---|---|
| **G1** | 需求有、用例无 | 规则无任何强匹配用例 | 功能整块漏测 | `coverage_audit.py` |
| **G2** | 覆盖了但场景失衡 | 模块无异常/边界用例，或全部负向用例中无权限校验类 | 只测顺利路径，缺陷全漏在异常侧 | `coverage_audit.py` |
| **G3** | 名义覆盖 | 1 条用例挂多条规则（`hit==1` 且规则文本跨度大） | 看着覆盖了，实际颗粒度撑不住 | `coverage_audit.py` |
| **G4** | **逃逸缺口**（有缺陷、无可拦用例） | 真实缺陷发生了，库内无任何 `expected` 能拦住它（或该模块库内 0 条用例） | 前三个都是"内部自洽"的缺口，G4 是**唯一有外部事实**的缺口 | `defect_audit.py`（见 `defect_loop.md`） |

> G1–G3 回答"需求有没有人测"，G4 回答"有人测了，为什么还是漏了"。优先级：**G4 > G1**——
> G1 至少还可能是"计划内没做"，G4 是"做了、也过了，但没拦住真的故障"。

---

## 三、匹配口径（避免假阳性的关键）

1. **显式标注优先**：用例有 `coverage_rule` 且 ID 在需求清单内 → 直接采信为强匹配，不再做文本匹配。
2. **文本相似度**：用例 `标题 + 步骤 + 预期 + 前置` 与规则文本做字符 **bigram Jaccard**，`>= --threshold`（默认 0.08）为强匹配。
3. **模块名只作候选、不作证明**：模块名相同但文本没达标 → 记为**疑似覆盖**，报告里单列"可能相关用例"，交人确认。
   - 这一条是硬性设计取舍：若允许模块名兜底计覆盖，任何同模块用例都会"覆盖"同模块所有规则，覆盖率虚高、报告失去意义。

---

## 四、报告结构（六节）

```markdown
# 用例覆盖率评审报告
- 输入 / 阈值 / 全局覆盖率

## 一、覆盖率概览
| 模块 | 需求功能点数 | 已覆盖 | 覆盖率 | 关联用例数 | 状态 |   ← 状态：✅达标 / ⚠️低于阈值 / ❌零覆盖

## 二、低覆盖模块（重点补充对象）

## 三、缺失用例清单（G1）
### <模块>
**完全缺失（无用例覆盖）**      1. R-00x 文本 → 建议用例类型 / 建议优先级
**疑似覆盖（需人工确认）**      - R-00x 文本 → 可能相关用例：TC-xxx

## 四、场景构成缺口（G2）
| 模块 | 正向 | 异常·边界 | 其中权限类 | 负正比 | 判定 |

## 五、名义覆盖风险（G3）

## 六、总结与建议
```

**建议用例类型 / 优先级**由规则文本推断（权限类 / 边界类 / 异常类 / 状态迁移 / 正交；P0 安全与主流程、P1 边界与异常、P3 显示与兼容），**推荐值不是结论**，最终定级仍以 `priority_p0_p3.md` 的五维评分 + R1–R7 为准。

## 四·五、双向追溯（RTM）与 Excel 第二 sheet

覆盖率报告是**模块级**的；RTM 是**需求级 + 双向**的补充，回答两个问题：

| 方向 | 问题 | 输出 |
|---|---|---|
| **正向** | 每条需求有没有人测？ | 需求 → 覆盖它的用例（含"部分覆盖"） |
| **反向** | 每条用例为什么存在？ | 用例 → 它验证的需求；无映射 = 孤儿用例 |

### 三元追溯（需求 ↔ 用例 ↔ 缺陷，v1.8.0）

二元 RTM（需求 ↔ 用例）只能证明"每条需求都有人测"，证明不了"测得住"。
补上缺陷这一维后，追溯变成三元，多回答一个问题：**这条需求下的用例，面对历史真实故障时会不会红？**

| 方向 | 问题 | 输出 | 命令 |
|---|---|---|---|
| **正向** | 每条需求有没有人测？ | 需求 → 覆盖用例 | `to_excel.py --with-rtm` / `coverage_audit.py --rtm-xlsx` |
| **反向** | 每条用例为什么存在？ | 用例 → 需求；无映射 = 孤儿 | 同上 |
| **外部** | 每条缺陷有没有可拦的断言？ | 缺陷 → 关联用例 / 缺口类型（G4） | `defect_audit.py --layer 3` |

**口径提示（别做过头的推断）**：
- 三元链条里，**只有"缺陷 → 无断言"这一环可靠**（`escaped`）；"缺陷 → 某条用例拦住了"不可靠（实测人工一致率 0/5），只能给候选、不能写进 RTM 的"已覆盖"列。
- 因此 RTM 第三维只落两列：`关联缺陷`（用例侧，可选第 12 列）与 `逃逸缺口 G4`（需求侧）。**不要**把 `suspected` 写成"已拦截"。
- 缺陷与需求的挂钩靠模块归一（`--module-map`），不要求需求侧有缺陷字段——这也是它能用在存量项目上的原因。

### 覆盖状态口径

| 状态 | 判定 | 含义 |
|---|---|---|
| **全覆盖** | 至少 1 条异常/边界/权限用例（或该需求只有负向用例） | 正向 + 负向都测了 |
| **部分覆盖** | 有映射用例，但**全部是正向** | 只测顺利路径，**不算真覆盖** |
| **未覆盖** | 无任何强匹配用例 | 整条需求漏测 |
| **孤儿用例** | 无 `coverage_rule`、文本/模块均未匹配 | 说不清"为什么存在"；`exploratory: true` 可豁免 |
| **疑似映射** | 仅模块名相同、文本未达标 | 需人工确认，不计孤儿 |

### 输出（Excel 第二 sheet「需求追溯」）

1. **需求覆盖矩阵**：需求ID / 模块 / 需求描述 / 优先级 / 覆盖状态 / 覆盖用例数 / 覆盖用例（编号）/ 缺口说明；状态着色（未覆盖红 / 部分覆盖黄 / 全覆盖绿），高优缺口置顶。
2. **孤儿用例**：编号 / 模块 / 用例名称 / 说明。
3. **疑似映射**（如有）：编号 / 模块 / 用例名称 / 疑似需求。

### 命令

```bash
# 主产物直接带 RTM（推荐）：用例 Excel 的第二个 sheet
python scripts/to_excel.py test_cases.json -o 功能测试用例.xlsx --with-rtm requirements.json

# 给已有 Excel 补写 / 刷新 RTM sheet
python scripts/coverage_audit.py test_cases.json requirements.json --rtm-xlsx 功能测试用例.xlsx
```

> 与预审第 10 项联动：`prescreen.py` 默认 `--orphan-max 0.0`，**任何孤儿用例直接阻断**；探索性用例请显式写 `"exploratory": true`。

### 缺陷侧追溯（G4）

```bash
# 缺陷 → 用例归属 + 缺口类型；--emit-backfill 出回归用例草案
python scripts/defect_audit.py bugs.json 功能测试用例.xlsx \
  --module-map module_map.json --layer 3 -o 缺陷反哺报告.md \
  --emit-backfill regression_backfill.json
```

- 输出的 `defect_map.json` 可直接与 RTM sheet 按**模块 + 用例编号**对齐，不需要改表结构。
- 用例侧要落"关联缺陷"列时用 `to_excel.py --with-defect`（可选第 12 列，主模板仍是 10 列）。

## 五、命令

```bash
# 生成后自审
python scripts/coverage_audit.py test_cases.json requirements.json -o 覆盖率报告.md

# 存量用例库评审（xlsx 直接读，无需先转 json）
python scripts/coverage_audit.py 历史用例库.xlsx requirements.json -o 覆盖率报告.md

# 收紧阈值 / 输出 JSON 供流水线消费
python scripts/coverage_audit.py cases.xlsx requirements.json --module-min 0.85
python scripts/coverage_audit.py cases.xlsx requirements.json --format json -o audit.json
```

退出码：`0` 全部模块达标 · `1` 存在低于阈值的模块 · `2` 输入/参数错误。

## 六、怎么用这份报告（不要直接照着补）

1. **先看第二节的排序**，从覆盖率最低、规则数最多的模块开始，不要平摊工作量。
2. **G1 逐条补**，但补之前先确认规则本身是否有效——过期需求应先标 `excluded` 再评审。
3. **G2 按配额补**：每个功能点 `1 正向 : ≥3 异常/边界`，且异常类里必须包含**权限校验**（未登录 / 无权限 / 跨角色越权）。
4. **G3 拆规则**：名义覆盖说明需求颗粒度比用例粗，要么拆用例、要么拆规则，不要放着不动。
5. **G4 只补断言不急着补用例**：逃逸缺口里绝大多数是"用例已存在但预期写成'正常显示'"，先往已有用例的 `expected` 里补数值/逐字文案/结果态，再谈新建。详见 `defect_loop.md` 第五节。
5. 补完后**重跑本脚本**，直到无 ⚠️/❌ 再进预审（`prescreen.py`）。

> 报告是**输入**不是**结论**：疑似覆盖必须人来判，脚本只负责把"没把握的地方"全部摆到桌面上。
