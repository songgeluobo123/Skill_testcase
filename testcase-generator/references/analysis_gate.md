# 分析闸门：两阶段流程 + 硬约束

本文件定义 `testcase-generator` 的**流程闸门与硬约束**：把"分析"与"生成"硬性分开，避免在需求理解有偏差时批量产出用例。

> 来源：参考业界实践（Shopee/Garena 的 `test-case-design` Skill 把"分析报告 → 用户确认 → 生成"设为硬闸门）与本技能既有检查点机制融合而成。
> 与其他文件的边界：字段写法见 `case_design.md`，预审阈值见 `quality_prescreen.md`，本文件只管**流程顺序与不可逾越的约束**。

---

## 一、两阶段流程（不可合并）

```
阶段 1  分析（Analysis）
  输入解析 → 多源获取 → 业务规则咨询 → 产出《测试分析报告》
        ↓
  🚧 硬闸门 STOP & ASK（等用户明确确认）
        ↓
阶段 2  生成（Generation）
  设计规范执行 → 自我评估 → 落盘 JSON → 导出 Excel → 总结报告
```

**硬闸门规则（强制）**：在收到用户明确确认前——

- ❌ 不得进入用例生成；
- ❌ 不得产出 `test_cases.json`；
- ❌ 不得导出 Excel；
- ✅ 只需交付《测试分析报告》并停下等待。

> 与既有检查点的关系：本闸门即 `workflow.md` 的**检查点⓪（最前置）**——先确认需求理解与测试范围，再在检查点①确认阈值与模板，两者都过才进入 Step 5/6。
> 用户在一句话里已给出"按此范围直接生成、不必再确认"的明确授权时，可跳过等待，但**报告仍须先产出并随交付一并附上**。

## 二、《测试分析报告》模板（阶段 1 唯一交付物）

```markdown
# 测试分析报告：{业务域 / 需求名}

## 1. 输入确认
- 业务域：{business_domain}
- 输入源：{PRD(链接) / UI 流程图 / XMind / 图片 / 本地文件 / 直接文本}
- 目标版本：{版本号}；语言：{zh / en}
- 未提供但影响生成的资料：{…}

## 2. 关键要点（每条必须带来源）
- {要点}（来源：PRD §3.2）
- {要点}（来源：知识库《XX 用例库》/ 专家问答 #3）
- {要点}（来源：MR !123 变更分析）

## 3. 信息缺口 / 待澄清（禁止自行补齐）
- ❓ {缺口 1}——影响：{阻塞主流程 / 边界 / 文案}
- ❓ {缺口 2}——影响：…

## 4. 建议测试范围与优先级
- P0：{横屏主流程、竖屏移植等价、各端联调}
- P1：{主流程拆解功能、等价类含异常、横屏布局适配、AI 数据准确性、监控灵敏度、数据安全}
- P2/P3：{显示完整性、美观与兼容}

## 5. 测试设计方法预选
- 每个主要功能点 → 拟用方法（等价类 / 边界值 / 场景法 / 状态迁移 / 判定表 / 正交）

## 6. 待办事项
A) 确认，继续生成
B) 补充信息如下：…
```

## 三、硬约束（五条，违反即返工）

| # | 约束 | 具体要求 | 落地位置 |
|---|---|---|---|
| H1 | **禁止假设** | 文档未写明的信息一律进「信息缺口/待澄清」，**不得编造补齐**；确需推进时只能标 `[假设]` 并经用户逐条确认 | 报告 §3；用例备注 |
| H2 | **业务规则咨询必须执行** | 生成前必须做一次"业务知识核对"（见下第四节），不得跳过；无可用知识源时**明确声明**"无专家知识可用"，不得假装问过 | 报告 §2 来源标注 |
| H3 | **术语一致性** | 严格保留需求原文术语：服务名 / 接口名 / 字段名 / 错误码 / 产品专有名词一律不改写、不翻译（如 `C00`、`S1-S4`、`CW/BW/ER/TP` 首次出现按"中文为主 + 英文括注"） | 标题与步骤用词 |
| H4 | **来源可追溯** | 关键要点与用例必须能回溯来源：文档章节 / URL / 知识库条目 / MR 号 / 需求规则 ID（`coverage_rule`） | 报告 §2；用例 `coverage_rule` / 可选 `source` |
| H5 | **多源融合要显式体现** | 若知识库/历史用例补充了需求文档没写的业务规则，必须在报告中写明"由 XX 补充"，不能静默合并 | 报告 §2 |

## 四、业务规则咨询（本技能中的"专家"）

原文实践里这一步是调外部专家平台；在本技能中，等价能力来自三个知识源，**按可用性依次尝试**：

1. **项目记忆**：`references/memory_mechanism.md` + 项目记忆文件（历史歧义、端侧约定、粒度偏好）。
2. **既有用例库 / 知识库**（如 ima 知识库、历史 Excel 用例）：优先检索同模块历史用例，看其前置、边界、失败判定口径。
3. **需求资料本身**（PRD / UI 流程图 / XMind / 图片）。

咨询分两类，与原文一致：

- **固定问题（每次必问）**：
  - 「该业务域有哪些测试注意事项？」
  - 「该业务域的关键业务规则是什么？」
- **动态缺口问题（针对报告 §3 逐条提问）**：
  - 例：「审核失败后的重试机制是什么？」「批量处理上限是多少？」

> 三个知识源都拿不到答案时：缺口照实列出并标注"无既有知识可用"，**不要用通用经验填充**。

## 五、变更分析（可选增强，有代码/变更信息时启用）

当用户提供 MR / diff / 变更说明时，在生成前补一步：

1. 列出**受影响逻辑**（改了什么、可能影响哪些路径）；
2. 按影响面**补充或调整用例**（如"新增重试次数限制""新增批量限流"）；
3. 在用例备注标注 `来源：MR !123（变更分析）`，并在报告 §2 记录。

无变更信息时跳过，不要凭空猜测改动点。

---

## 六、生成后的五项自我评估（与预审互补）

生成完成、跑 `prescreen.py` 之前，先自问五句，任一为"否"就修正后再出库：

1. **优先级**：P0 是否覆盖了最高风险点（横屏主流程 / 竖屏移植等价 / 联调）？
2. **术语**：是否保留了需求原文术语，没有自行改写或翻译？
3. **无假设**：是否混入了未经确认的假设（有则回填到信息缺口）？
4. **覆盖度**：正向 / 负向（异常）/ 边界 三类是否都有，同构组是否 ≥3 条？
5. **可追溯**：每条用例是否都能指回需求规则 ID 或来源章节？

## 七、阶段 2 交付物（固定四件）

| 交付物 | 说明 |
|---|---|
| 用例 JSON | `test_cases.json`（字段见 `output_format.md`；含 `coverage_rule` / `design_method` / 可选 `source`） |
| Excel | `to_excel.py` 导出（默认 10 列，需分列时 `--with-environment` 11 列），**单个文件覆盖原文件** |
| 总结报告 | 用例总数 + P0–P3 分布 + 咨询回顾（问了什么、是否有效、补充了什么） |
| 分析报告 | 阶段 1 的报告终稿（留档，随交付附上） |

> 总结报告中的"咨询回顾"要如实写：哪些问题拿到了有效信息、哪些没有（原文实践里也允许出现"⚠️ 无有效信息，已基于文档提取"）。
