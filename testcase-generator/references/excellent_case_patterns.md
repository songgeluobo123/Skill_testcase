# 优秀用例的实证模式（可复制做法与反面清单）

本文件是 `testcase-generator` 的**经验证据层**：从一份真实优秀用例库（EQI 智能出行，1278 条，含 APP / 嵌入式固件 / 联调功能 / 系统后台 4 个技术域）中逐行统计、反推出来的可复制做法与踩坑清单。

> **与其它文件的边界**：本文件不重复定义规则——字段定义见 `references/output_format.md`，命名红线见 `references/naming_rules.md`，编写原则见 `references/case_design.md`，预审阈值见 `references/quality_prescreen.md`。本文件只回答一件事：**"写得好"在真实库里长什么样，生成时具体怎么落地。**

---

## 一、十个可复制做法（每条附实证与落地要求）

### 做法 1：双前置列分离——「测试环境」公共复用 + 「前置条件」本条状态

优秀库把"条件"拆成两列，职责完全不同：

| 列 | 职责 | 写法 | 复用度（实证） |
|---|---|---|---|
| **测试环境** | 可整块复制的环境准备清单 | 编号式：`1.手机连接可用网络` / `1.手机连接可用网络 2.滑板车设备上电` | 1271 条只用了 **53 个不同值**，最大一条 `手机连接可用网络` 被 **602 条**共享 |
| **前置条件** | 本条用例操作前的界面/状态 | `已进入启动界面` / `在"设备设置"界面` | 845 个不同值 / 1271 条（**几乎不复用，是碎片化的**） |

**落地要求（生成时）**：
- 每条用例**同时输出**这两列；公共环境用**编号清单**收敛为有限模板（全库模板数应远小于用例数，建议 ≤ 用例数的 10%）。
- 界面/状态类条件写进「前置条件」，**不要**混入「测试环境」；环境准备也不要写进「前置条件」。
- 反面实证：该库两列语义已经漂移（`测试环境` 里出现 `滑板车上电（电源已关）` 这类状态、`前置条件` 里出现 `90s<T<300s` 这类硬指标），**同一信息两处可写 → 长期必然漂移**，生成时必须守住边界。

### 做法 2：步骤动词白名单，动作粒度到"按钮名 / 界面名"

实证动词频次：`查验` 670、`点击` 488、`输入` 169、`设置` 126、`选择` 65、`关闭` 41、`上传/下载` 各 12、`对比` 15。**"看看 / 测一下 / 验证下"这类描述性文字几乎不存在。**

- ✅ `点击"检查固件更新"列表，进入"检查版本"界面`（原文）
- ✅ `短按"获取验证码"按钮`（原文）
- ✅ `查验APP启动界面的UI元素`（原文）

**落地要求**：步骤必须以 `点击 / 输入 / 勾选 / 查验 / 进入 / 设置 / 选择 / 关闭 / 上传 / 下载 / 对比 / 记录 / 短按 / 长按` 之一开头；按钮名、界面名、输入值必须写具体。**"查验"式步骤必须指明查验对象**，不得裸写"查验功能"。

### 做法 3：预期结果写成"应…"断言句，且可判定

实证：含"应"字的预期 **1055 / 1271 = 83%**；多行清单化预期 419 条（32.8%）；含具体数字的预期 496 条（38.8%）。

三种可判定形态（都要用）：
1. **UI 元素清单化**：`应覆盖的UI元素：1.品牌宣传图 2.应用名称 3.加载图标 4.无任何操作执行元素（自动跳转启动并进入登录界面）`（原文）
2. **数值 / 阈值化**：`在IOT系统的物模型界面中查看到公英制属性值为：0`、`通过率高于95%`、`90s<T<300s`（原文）
3. **文案逐字校验**：`应弹出提示信息："长度8位，需要含数字和字母"（国外版本英文提示，翻译内容接近）`（原文）

**落地要求**：预期一律用"应…"或数值断言收尾；凡涉及 UI → 给元素清单，涉及提示 → 给逐字文案（含多语言差异），涉及数据 → 给具体值或阈值。**禁止**"合理 / 美观 / 流畅 / 友好 / 正常显示 / 无异常"等无判定标准的描述。

### 做法 4：主动产出"同构组"（模板化批量覆盖，不重不漏）

优秀库里大量用例是**同一模板换参数**，且每组成组出现：

| 同构组类型 | 实证 | 条数 |
|---|---|---|
| 等价类（运营商） | `可使用中国移动卡进行一键登录` / `中国联通卡` / `中国电信卡` | 3 |
| 边界值（验证码超限） | `在验证码登录中获取验证码超过10次能被冻结` + 修改密码 / 注册 / 注销 三个界面 | 4+1 |
| 权限矩阵 | 已同意/未同意 × 相册 / 相机 / 定位 | 5 |
| 状态迁移（旧验证码失效） | 修改密码 / 注册 / 注销 三界面各一条 | 3 |
| 多入口触发 | 开机：`通过APP开机功能正常` / `通过滑板车设备开机功能正常` / `通过系统开机功能正常` | 3（关机同理） |
| 参数×时长×模式耐久 | `挂测48小时` / `保持10米距离挂测48小时` / `行人模式骑行过程中挂测8小时` / `E节能模式` / `D标准模式` / `S运动模式` | 6 |
| 同功能按端拆分 | `设备状态与设置` 在 APP(202) / 嵌入式固件(166) / 联调功能(113) 三域各有用例 | 481 |

**落地要求**：Step 5 生成用例时，**每一个等价类 / 边界值 / 权限矩阵 / 多入口 / 多模式测试点，必须成组输出 ≥3 条**，组内只有参数不同、其余字段同构；同功能若涉及多端（APP / 固件 / 后台 / 联调），按端拆套而不是重复描述。

### 做法 5：标题句式——「对象 + 场景 + 功能正常 / 应…」，无编号、无句末标点

实证（1278 条）：
- 以数字编号开头：**0 条**；含逗号/句号等句末标点：**0 条**；平均 **18 字**（4–41 字）。
- 三大主导句式：① `…功能正常` 283 条（如 `APP进入功能正常`）；② `…应…` 断言式 186 条（如 `一键登录界面获取到的手机号应明文显示`）；③ 条件前置式：以"在"开头 191 条 / "当" 52 条 / "通过" 22 条（如 `弱网环境OTA升级正常`、`当滑板车处于行人模式骑行过程中挂测8小时蓝牙一直保持连接`）。
- 数值写进标题 87 条（`挂测48小时`、`超过10次能被冻结`）。
- 反面实证（要避免）：`验证码界面中当输入框输入数据正确且协议书复选框已勾选登录按钮可用`——38 字、条件堆叠无分隔、主谓不明。

**落地要求**：标题 ≤20 字（本技能红线，见 `naming_rules.md`），不带编号与句末标点；条件过多时**拆到前置条件列**，不要堆进标题。

### 做法 6：非功能覆盖 =「场景化前置 + 量化预期 + 数据外置」三件套

该库**没有**"兼容性测试/安全测试/异常测试"这类类型标签（"兼容"二字命中 0 次），非功能全靠写法落地：

| 维度 | 场景化前置（原文） | 量化预期（原文） |
|---|---|---|
| 弱网 | `手机当前连接的是网速较慢的网络（例如：高延迟、低带宽的网络）` | `OTA包能正常下载到APP手机中` / `OTA包下载完整` / `OTA包安装到滑板车正常` |
| 性能 / 耐久 | `设备已开启日志记录` / `APP已开启日志记录` / `准备挂测表格` | `每次查验APP手机与滑板车设备蓝牙应保持连接状态` / `滑板车日志中未出现蓝牙断连日志` |
| 压测 | 测试数据列挂统计表名 | `APP应能升级成功（或升级通过率高于95%）` |
| 异常 / 中断 | `滑板车在OTA升级过程中弹出异常报警` | `滑板车OTA升级应立即停止` |
| 安全 / 隐私 | `已进入一键登录界面` | `显示的手机号应中间四位加密` |

**数据外置**：量化数据不塞进用例（该库 `测试数据` 列仅 22 条非空，全部指向统计表：`OTA升级压测统计表`、`APP升级-启动速度测试统计表` 等），用例内只留**统计表名引用**。

**落地要求**：非功能用例必须"弱网给指标定义、耐久给时长、压测给次数与通过率、异常给触发条件"，原始数据指向统计表名，不在用例里堆原始数据。

### 做法 7：版本 / 端 / 机型维度落到标签列，并做覆盖均衡检查

该库用 **APP版本类型**（国内/国外）、**移动端类型**（Android/IOS）、**设备型号**（公共/BB2/BB3）三个标签列表达兼容维度，并在预期里固定追加多语言要求 `（国外版本英文提示，翻译内容接近）`（"翻译"命中 32 条）。

**反面实证（必须避免）**：`移动端类型` **991 条为空（77.5%）**；已填的 287 条里 Android 224 条、**IOS 仅 1 条单值**——覆盖严重不均，维度列形同虚设。

**落地要求**：生成后**强制做覆盖均衡检查**：任一标签列的取值分布不得出现"某取值 ≤3 条而另一取值 >100 条"的失衡；受影响用例的预期必须带上多语言/多端差异要求。

### 做法 8：缺陷闭环写进行内，实际结果只在失败时填

- `备注` 列直接挂缺陷单：`详见BUG：【【APP】【IOS】【一键登录功能无效】使用电信卡一键登录功能无法使用】https://www.tapd.cn/…`（原文，含单号与状态）。
- `实际结果` 只在"实际 ≠ 预期"时填写（该库 111 / 1278 条非空）。
- 反面实证：第 372 行把**执行困难**（`不知道车辆怎么恢复出厂设置`）填进了 `实际结果` ——**"执行不了"不是实际结果**，应进备注或问题记录。

**落地要求**：生成/交付时明确三件事——① 备注用于挂缺陷单号+状态；② 实际结果仅记录实测与预期的差异现象；③ 阻塞/无法执行的原因进备注，不污染实际结果。

### 做法 9：优先级纪律——主干占七成，审美类不滥发

实证分布：P1 41.1% / P0 30.2% / P2 22.1% / P3 5.8% / P4 0.6%。**P0+P1 = 71.3%**，重心压在主干链路；审美类只占极小比例。

**落地要求**：与 `priority_p0_p3.md` 的占比建议联动校核；主观类（布局美观等）用例总量应保持在个位数百分比，且必须补判定基线（参考图/设计稿），否则不生成。

### 做法 10：生成即体检——去重、残缺、占位残留三项必查

反面实证（同一份优秀库里仍存在的问题，正是本技能要提前拦住的）：
- **56 组标题重名**（最多重复 3 次，如 `组合键解锁功能正常`），且**全表没有"用例编号"列**，无法区分 → 该库最大的结构性缺陷。
- **7 条残缺用例**（无步骤/无预期/无类型，3 条连优先级也空）混在库中，集中在"嵌入式固件｜设备状态与设置"。
- **9 条标题带 `（待BOE表更新）` 类未完成标记**仍留在库内。
- 书写不一致：`Android, IOS` 与 `IOS, Android` 两种顺序混用；笔误如 `界面UI排列公正`（应"工整"）、`查验OTA相应`（应"响应"）、`应提示提示"…"`（叠字）。

**落地要求**：出库前跑三项自检——① 标题查重（重名必须靠唯一 ID 区分）；② 残缺检查（步骤/预期/优先级/类型任一为空即阻断）；③ 占位残留扫描（`待XX更新`、`TBD`、`XXX` 一律不入库）。枚举型字段的取值顺序全库统一。

## 二、生成后自检清单（逐条打勾，任一不满足即回退）

- [ ] 每条用例都有「测试环境」（编号式、来自有限模板）+「前置条件」（本条状态），两列语义不混。
- [ ] 每条步骤以动词白名单开头，按钮/界面/输入值具体，"查验"类指明对象。
- [ ] 每条预期均为"应…"或数值断言，UI 给元素清单、文案给逐字内容、数据给具体值。
- [ ] 预期无"合理/美观/流畅/友好/正常显示"等不可判定词。
- [ ] 每个等价类/边界/权限矩阵/多入口/多模式测试点，均以 ≥3 条同构成组输出。
- [ ] 非功能用例具备"场景化前置 + 量化预期 + 统计表引用"三件套。
- [ ] 版本/端/机型标签列分布均衡，多语言用例已带差异要求。
- [ ] 全库标题无重名（或有唯一 ID 区分）、无占位残留、无残缺条目。
- [ ] 枚举字段取值顺序全库统一。

## 三、反面清单速查（见到即改）

| 反模式 | 反例（原文） | 修正 |
|---|---|---|
| 不可判定预期 | `界面UI排列公正`、`界面颜色搭配合理` | 给设计稿基线 + 可量化的对齐/间距/颜色值判据 |
| 条件堆进标题 | `验证码界面中当输入框输入数据正确且协议书复选框已勾选登录按钮可用` | 拆到前置条件，标题收敛为 `协议书已勾选时登录按钮可用` |
| 实际结果填成"执行困难" | `不知道车辆怎么恢复出厂设置` | 移入备注/问题记录，实际结果留空或填实测差异 |
| 无唯一 ID 导致重名不可辨 | 56 组重名标题 | 强制输出用例编号列 |
| 维度列大面积为空 | `移动端类型` 空 77.5%，IOS 单值仅 1 条 | 生成后做覆盖均衡检查 |
