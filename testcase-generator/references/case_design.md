# 测试用例设计原则与编写规范

Step 5 把 Step 3 测试点转化为可执行用例时，强制遵守本文件。本文件是**用例编写规范的唯一权威来源**：设计原则、四字段写法、测试类型转化、优先级口径、粒度习惯均在此统一描述，避免规则散落多文件导致口径不一。

> 命名红线（R1–R7）单独立规于 `references/naming_rules.md`；Excel 列容器与 JSON 字段定义见 `references/output_format.md`；P0–P3 口径见 `references/priority_p0_p3.md`。

---

## 一、10 条设计原则（强制）

1. **可执行性**：每个用例必须能被任何人独立执行（前置条件 / 步骤 / 预期完整）。
2. **单一验证**：一个用例只验证一个核心业务场景或规则；端到端流程除外。
3. **用例命名规范**：名称体现测试工作内容，精简 ≤20 字，不含预期结果，不用数字前缀（1、2、3），不用【】标记模块 / 按钮。7 条强制红线见 `references/naming_rules.md`。
   - ✅ `正确密码登录`、`错误密码登录`、`空用户名登录`
   - ❌ `1、【登录】输入正确密码，登录成功`
4. **格式规范**：前置条件 / 步骤 / 预期均换行分隔，且各自用编号 `1. 2. 3.` 开头（格式细节见「二、四字段编写规范」）。
5. **步骤 = 预期一一对应**：步骤数 = 预期数（详见「二、三 / 二、四」）。
6. **拆分 / 合并原则**：正向连续操作合并；反向校验 / 边界值 / 无效等价类每个独立拆分为独立用例。
7. **用户视角一致**：单个用例保持视角一致，核心完整流程可跨角色合并。
8. **用例独立性**：用例之间无显式依赖，数据通过前置条件准备。
9. **步骤数量控制**：每个用例不超过 5 条操作步骤（详见「二、三」）。
10. **预期可验证 / 数据具体**：不写"正确显示"，写具体内容和跳转动作；不写"合法值"，写"张三"（详见「二、四」）。

## 二、四字段编写规范（标题 / 前置条件 / 测试步骤 / 预期结果）

> 适用于输出用例的「用例名称 / 前置条件 / 测试步骤 / 预期结果」四列。
> Step 5 生成**每条**用例时，强制按本节逐字段约束；命名红线见 `references/naming_rules.md`。

### 一、用例标题

- **定位**：用简洁概括性语言体现**关注点与出发点**，使协作人员（执行人 / 评审 / 产品）快速理解意图，并判断测试点覆盖是否遗漏。
- **编写方式（任选其一）**：
  - 功能点：如 `网络正常时点击购买按钮弹出支付弹框`
  - 功能-流程：如 `会员购买页面-成功购买流程`
  - 状态或条件-结果：如 `无网状态-点击购买-提示无网`
- **与模块名结合**：格式为 `模块名-测试标题`，表示"在测试标题情况下测试该模块"。
- **锁定机制**：标题定下后即锁定用例中心点，前置条件、步骤、预期**均须围绕其展开**，不得发散。

### 二、前置条件

- **定义**：执行用例需满足的**条件或准备操作**（测试数据、角色权限、进入页面、展示弹框等）。
- **两大原则**：
  1. 条件本身**必须成立**；
  2. 该条件下，**后续步骤必能成立**（不再因前置缺失而中断）。
- **按需使用**：非所有用例都需前置条件，应在确认测试点后再判断是否必要。
- **确定方法**：列出"到达测试点"所需的全部步骤与预期，**保留关键步骤**，其之前的内容**归纳为前置条件**。
- **典型场景**：
  - 明确待测状态（如：已登录）；
  - 控制变量（除待测项外，其余已填 / 已就绪）；
  - 准备数据 / 页面 / 弹框；
  - 用例间关联（前置引用另一用例的预期结果）。
- **产出形态**：最终将条件**归纳为简洁结果**（不用冗长操作描述）。

### 三、测试步骤

- **定义**：验证测试点所需的**线性操作**——先做什么、后做什么。
- **描述要求**：清晰准确，**不出现假设性词语**；页面名、按钮名 / 位置须**明确**可定位。
- **围绕标题**：围绕标题展开，多余步骤**归入前置条件**；单用例步骤不超过 5 条（原则 9）。
- **禁止连词**：不出现「和 / 或 / 且」等连词，违者**拆分步骤**（一步一动作）或**拆分用例**。
- **不含预期**：不含预期结果内容，严格区分"步骤"与"预期"两列；步骤数 = 预期数（原则 5）。

### 四、预期结果

- **定义**：完成步骤后程序的**表现**，即检查点。
- **围绕测试点**：围绕标题 / 测试点描述，**不有多余或遗漏**检查点。
- **不含步骤**：不含测试步骤（与步骤严格分离）。
- **数量下限**：每条用例**至少一**条预期结果。
- **检查点形态**：含界面表现、数据库数据、保存文件或其他**可验证表现**（不写"正确显示"，写具体内容 / 跳转动作，见原则 10）。

### 五、生成时字段联动自检（优化生成逻辑）

生成每条用例后，按以下链路逐字段核对，使四字段一致、不重不漏：

1. **标题锁定中心点** → 标题是否含预期判定词（R2）？是否 ≤20 字、无序号前缀、无【】、术语统一（见 `naming_rules.md`）？
2. **前置条件只放"标题成立前必须就绪"的内容** → 是否存在应在步骤里的操作被误放前置？条件是否自身成立且能支撑后续步骤？
3. **步骤是标题内待测操作的线性序列** → 是否含"和/或/且"（拆）？是否混入预期（移）？页面/按钮是否明确？是否 ≤5 步？
4. **预期逐步骤对应检查点（至少 1 条）** → 是否缺失？是否含步骤？是否可验证（界面/数据/文件）？

> 联动原则：**标题 → 前置 → 步骤 → 预期** 自上而下收敛，任一字段越界（步骤写成预期、预期写成步骤、前置含待测操作）均回退修正后再生成下一条。

## 三、不同测试类型的转化要点

| 测试类型 | 特点 | 转化要点 |
|---|---|---|
| 正向 / 反向测试 | 验证功能是否实现 | 覆盖所有需求条目，按用户习惯设计步骤，预期明确对应需求描述 |
| 异常 / 边界测试 | 验证系统健壮性 | 明确异常触发条件，预期强调"优雅失败"，关注错误提示准确性 |
| 模块交互测试 | 验证模块间交互和数据流 | 关注接口与数据边界，验证数据一致性，含异常数据流 |
| 用户场景测试 | 验证端到端业务体验 | 业务闭环，真实数据流，多角色协同，状态流转验证 |

## 四、优先级划分标准（P0–P3）

本技能统一采用 **P0–P3** 四级优先级（**不再使用 P1–P4 体系，无 P4**）。完整定义、五维评分模型、硬规则决策表、质量属性 / 各端映射、分级 SOP 见 `references/priority_p0_p3.md`（优先级分级的**唯一权威来源**）。

| 级别 | 颜色 | 范围 | 执行要求 |
|---|---|---|---|
| **P0** | 🔴 红 | 冒烟/核心链路/安全合规/数据正确性/固件可用性（一票否决） | 每次构建必跑，100% 通过方可发布 |
| **P1** | 🟠 橙 | 重要功能/高频场景/主流兼容/安全属性/易用主路径 | 每轮主测试（SIT/回归主集）必覆盖 |
| **P2** | 🔵 蓝 | 一般功能/次要场景/低频兼容/部分性能可靠边界 | 常规迭代覆盖，回归可选 |
| **P3** | ⚪ 灰 | 极端边界/探索性/极低频配置/纯体验细节 | 全量或探索性按需覆盖，不计入发布门禁 |

> 生成用例时 `priority` 字段仅可取 `P0` / `P1` / `P2` / `P3`，不得出现 P4 或其它分级。具体定级依据（五维评分 D1–D5 加权 + R1–R7 硬规则 + 各级范围 / 执行 / 评审 / 示例）以 `references/priority_p0_p3.md` 为唯一权威来源，本文件不另立映射口径。

## 五、粒度学习要点（来自历史模板）

- **前置条件粒度**：数据少时指定具体名称，数据多时概括描述。
- **步骤描述粒度**：核心 / 首次操作详细，重复 / 相似操作概括。
- **预期对应关系**：步骤数 = 预期数，一一对应。
- **用例命名习惯**：遵循 `references/naming_rules.md` 红线，名称不体现预期结果。
