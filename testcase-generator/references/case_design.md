# 测试用例设计原则与格式规范

Step 5 把 Step 3 测试点转化为可执行用例时，强制遵守以下规范（来自历史编写习惯沉淀）。

---

## 一、10 条设计原则（强制）

1. **可执行性**：每个用例必须能被任何人独立执行（前置条件 / 步骤 / 预期完整）。
2. **单一验证**：一个用例只验证一个核心业务场景或规则；端到端流程除外。
3. **用例命名规范**：名称体现测试工作内容，精简 ≤20 字，不含预期结果，不用数字前缀（1、2、3），不用【】标记模块 / 按钮。
   - ✅ `正确密码登录`、`错误密码登录`、`空用户名登录`
   - ❌ `1、【登录】输入正确密码，登录成功`
4. **格式规范**：前置条件 / 步骤 / 预期换行分隔；**前置条件、步骤、预期都用编号 1. 2. 3.** 开头。
5. **步骤=预期一一对应**：步骤数 = 预期数。
6. **拆分 / 合并原则**：正向连续操作合并；反向校验 / 边界值 / 无效等价类每个独立拆分为独立用例。
7. **用户视角一致**：单个用例保持视角一致，核心完整流程可跨角色合并。
8. **用例独立性**：用例之间无显式依赖，数据通过前置条件准备。
9. **步骤数量控制**：每个用例不超过 5 条操作步骤。
10. **预期可验证 / 数据具体**：不写"正确显示"，写具体内容和跳转动作；不写"合法值"，写"张三"。

## 二、不同测试类型的转化要点

| 测试类型 | 特点 | 转化要点 |
|---|---|---|
| 正向 / 反向测试 | 验证功能是否实现 | 覆盖所有需求条目，按用户习惯设计步骤，预期明确对应需求描述 |
| 异常 / 边界测试 | 验证系统健壮性 | 明确异常触发条件，预期强调"优雅失败"，关注错误提示准确性 |
| 模块交互测试 | 验证模块间交互和数据流 | 关注接口与数据边界，验证数据一致性，含异常数据流 |
| 用户场景测试 | 验证端到端业务体验 | 业务闭环，真实数据流，多角色协同，状态流转验证 |

## 三、优先级划分标准（P1–P4）

| 级别 | 含义 | 示例 |
|---|---|---|
| **P1** | 核心正向 / 冒烟，最高业务影响 | 支付成功后订单生成、登录成功 |
| **P2** | 重要功能 | 优惠券核销、列表筛选 |
| **P3** | 完整验证 | 表单全字段校验、导出全字段 |
| **P4** | 增强 / 探索 | 极端值探索、兼容性、UI 细节 |

> 优先级映射维度：业务影响度（高 / 中 / 低）× 用户频率（高频 / 低频）。核心高频 = P1。

## 四、粒度学习要点（来自历史模板）

- **前置条件粒度**：数据少时指定具体名称，数据多时概括描述。
- **步骤描述粒度**：核心 / 首次操作详细，重复 / 相似操作概括。
- **预期对应关系**：步骤数 = 预期数，一一对应。
- **用例命名习惯**：自由描述，不体现预期结果。
