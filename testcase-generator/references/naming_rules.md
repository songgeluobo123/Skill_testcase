# 测试用例命名规则

> 适用于 `testcase-generator` 输出的「用例名称」列。命名评审（检查点）必查以下红线。

## 一、目的与原则

1. **一眼看懂**：任何人（执行人、评审、产品）看到名称即知"测什么"，无需打开步骤。
2. **名称 ≠ 预期**：名称只描述**测试意图 / 操作 / 对象**，判定结论（成功/正确/通过）写在「预期结果」列，不进名称。
3. **可检索、可聚合**：统一术语与结构，便于按模块、分端、分质量属性筛选统计。
4. **单一对应**：一个名称对应一个核心场景（与"单一验证"设计原则一致）。

## 二、强制规则（红线，命名评审必查）

| #  | 规则                          | 反例                    | 正例                  |
| -- | --------------------------- | --------------------- | ------------------- |
| R1 | 长度 ≤ 20 字（精简）               | `使用正确密码在登录页输入并完成登录操作` | `正确密码登录`            |
| R2 | 不含预期结果 / 判定词（成功、正确、通过、正常显示） | `密码正确登录成功`            | `正确密码登录`            |
| R3 | 不用数字序号前缀（1、2、3…）            | `1、登录成功`              | `正确密码登录`            |
| R4 | 不用【】/[] 包裹模块或按钮名            | `【登录】输入正确密码`          | `正确密码登录`            |
| R5 | 不堆砌"测试/验证/用例"冗余前缀           | `测试登录功能`              | `正确密码登录`            |
| R6 | 术语统一（同义不同写算不合格）             | 时而`登录`时而`登陆`          | 统一用`登录`             |
| R7 | 不用模糊量词（各种、若干、正常情况）          | `各种网络下启动训练`           | `弱网启动训练` / `断网启动训练` |

## 三、用例编号规范（与名称规则分开管理）

编号是**追溯锚点**（缺陷挂单、覆盖率映射、备注注入都靠它），名称是**可读描述**，两者不要混。

- **格式**：`TC-{模块缩写}-{3 位序号}`，如 `TC-LOGIN-001`、`TC-PAY-012`、`TC-C00-003`。
  - 模块缩写取 2–6 位大写字母/数字，沿用项目既有术语代号（`LOGIN` / `PAY` / `OTA` / `C00` / `BLE`），**不要缩写到无法辨认**（`TC-A-001` ✗）。
  - 中文模块名无既有英文代号时，在项目术语表里定义一次并全局复用，不要同模块出现两种缩写。
- **必须显式写 `id`**：`scripts/to_excel.py` 在用例 JSON 无 `id` 时按出现顺序生成 `TC-001`，**序号会随增删用例整体漂移**，导致历史缺陷单号对不上。生成器必须在构造用例时写死 `id`。
- **全局唯一**：重复编号判为阻断项（见 `prescreen.py` 第 8 项）。同模块标题可以重名，但编号不能重复。
- **编号不进标题**：不要把 `TC-LOGIN-001` 写进「用例名称」列，编号只出现在「用例编号」列。
