# 存量库规范化（Step 7：接手历史用例时用）

> **一句话**：技能原本只有「从零生成」（Step 1→6）。真实工作里更常见的是**接手 900 条历史用例做规范化**——这些库往往功能流程齐全，但结构、标题、数据、优先级、重复度全线走形。
>
> **不要重写，要分诊**：存量库的每一条都可能是某人某次评审改过的结果，机械重写会丢掉历史意图。Step 7 的原则是**先体检、再分类、机械项脚本改、判断项人工过、最后整库过闸门**。

---

## 一、七类典型问题（按修复收益排序）

| # | 问题 | 判据 | 修复方式 | 风险 |
|---|---|---|---|---|
| 1 | **结构与语义错位** | 前置条件里写操作动作（「点击X后进入Y」）而非状态 | 拆分：可复用环境 → `测试环境`；界面/状态 → `前置条件`（做法 1） | 低（机械可拆） |
| 2 | **标题含空泛判定词** | 命中 `成功/正确/正常/通过/无异常` | 改写成「对象 + 操作」，具体结果短语可留（`naming_rules.md` R2 口径） | 低 |
| 3 | **步骤不可执行** | 无动词白名单（点击/输入/查验…）或「点击按钮」未说明位置/容器 | 补动词与位置；**不靠加字数凑**（`score_testcases.py` 语义判据） | 中（需理解用例意图） |
| 4 | **测试数据无效** | 占位符（`test01`/`xxx`/`待定`）、字段与类型不匹配 | 按业务规则填真实值；无数据依赖的用例留空并在备注说明 | 中（要知道合法取值域） |
| 5 | **优先级失衡** | P0 占比 >25% 或 <10%、P2 不在 25%~40% | 按 `priority_p0_p3.md` 五维评分重定级 | 中（定级要一致口径） |
| 6 | **语义重复** | 同模块 + 同前置 + 同步骤 + 同预期 | 合并保留信息最全的一条，其余删除或改造成**并列场景**（不同数据/不同入口） | 高（易误删有价值用例） |
| 7 | **范围性用例** | 一条覆盖多个并列子场景，预期只有 1 条断言 | 备注列逐项展开，或按子场景拆条（`case_design.md` 第七节判定表） | 中 |

**修复顺序不可颠倒**：先 1/2（结构语义）→ 再 3/4（可执行性）→ 再 5（优先级，依赖前两步的语义清晰）→ 最后 6/7（合并与拆分，依赖全库语义已稳定）。**先合并再改标题会导致合并判据失真**——两条"看起来重复"的用例，标题改准后可能根本不是一回事。

## 二、三步工作流

### 7.1 体检（只读，不改库）

```bash
python scripts/normalize_legacy.py 存量库.xlsx -o 存量库体检.md
```

输出七类问题清单，每条含：问题样本、影响条数、**是否机械可修**、建议动作。先看这份报告决定改哪些、哪些接受现状。

### 7.2 分项修复

- **机械项**（结构拆分、标题空泛词、数据占位符、优先级公式重算）：用脚本批量，改前备份 `_before_normalize_<日期>.xlsx`，改后**逐格校验**（差异格数 == 计划格数，计划外 0）。
- **判断项**（步骤改写、重复合并、拆条）：逐条人工过，每条在备注列记「原写法 → 新写法 + 理由」，便于回溯。
- **不接受现状也要留痕**：确实无法修的（如历史遗留的模糊需求），在备注标 `[遗留]`，不要假装它合格。

### 7.3 回归与归档

```bash
python scripts/prescreen.py 修复后.json --requirement-rules 需求规则.json \
       --min-cases-per-rule 4 --density-mode block \
       --matrix ./testpoint/等价类边界值矩阵.md \
       --single-case-mode block --ui-cover-mode block --nf-cover-mode warn \
       --range-mode block --method-check block --scene-rule-mode block
python scripts/score_testcases.py 修复后.json
```

- 闸门参数按存量库实际情况放宽（历史库多半无矩阵、无 coverage_rule，对应项会跳过或告警——**跳过不等于通过**，报告里要写清）。
- 归档：修复前后条数/类型分布/优先级分布对照 + 闸门结论变化，一页纸即可。

## 三、与其它 Step 的关系

| Step | 关系 |
|---|---|
| Step 1–6（从零生成） | 存量库规范化**不走** Step 1–3（需求分析、测试点）；直接进用例层 |
| Step 3.5（矩阵） | 历史库通常没有矩阵。补矩阵的价值在于**暴露缺哪些等价类**，可作为 7.2 之后的可选增强 |
| `coverage_audit.py` | 回答「需求覆盖够不够」；Step 7 回答「已有用例写得规不规范」——两者互补，先跑哪个都行，但**都要跑** |
| `mutation_audit.py` | 规范化完成后跑一次强度审计；其中「规则不可测量」属需求侧问题，不计入用例得分（1.12.1 起分账） |

## 四、红线

1. **不为了过闸门而扭曲语义**。若闸门判你误报（如位置词表不认「弹窗底部」），描述清楚并反馈规则缺口，不要改写成别扭措辞凑白名单。
2. **合并/删除前必须双人确认**。语义重复的误判成本最高——两条用例可能因前置不同而都是有效的（`case_design.md` 第七节「多入口一律拆条」）。
3. **优先级重定级要用同一把尺**。全库一次性重算，不要局部调；局部调必然产生新的不平衡。
4. **改完必须回归**。存量库规范化的失败模式不是"改错"，而是"改完没人再跑闸门"，三个月后又漂回去。
