# UI / 视觉 / 文案用例设计（六类生成规则）

> **一句话**：功能用例回答「做了这件事，系统行为对不对」；UI 用例回答「这件事在屏幕上**长什么样、什么状态、什么字**」。两条腿缺一条，页面功能对但显示错的产品照样流出。
>
> **数据依据**：某优秀用例库 1278 条中 UI 族（界面交互 / UI 元素 / 文字查验 / 用户体验 / 模块交互）509 条占 **40%**，其预期 **87% 含可观察视觉词**；纯功能用例的预期只有 33% 含视觉词。差距就是这批规则要补的。

---

## 一、六类 UI 用例与生成公式

| # | 类型 | 回答什么 | 生成公式 | 典型标题 |
|---|---|---|---|---|
| 1 | **界面交互测试** | 触发后控件的反馈与跳转 | 触发动作 + 控件 → **反馈的视觉表现** | 在灯光设置界面选择"闪烁"后选项框变蓝 |
| 2 | **UI 元素测试** | 页面/弹窗的元素清单 | 进入页面 → **逐项枚举**：元素名 + 类型 + 视觉属性 | 删除账号验证界面 UI 元素显示完整 |
| 3 | **文字查验测试** | 界面文字的规范与颜色 | 查验文字 → 错别字 / 敏感词 / **占位符逐字** / **逐状态颜色** | 验证码输入框占位符信息正确 |
| 4 | **数据展示测试** | 数据在 UI 上的精度与格式 | 数据源 → 精度 / 单位 / 格式化规则 | 骑行记录总里程四舍五入显示 |
| 5 | **用户体验测试** | 环境切换下的表现 | 环境切换（网络/弱网/中断） → 主功能不中断 | 从电信网切换到 WiFi 网 OTA 升级正常 |
| 6 | **模块交互测试** | 一次操作在**每个受影响端**的反馈 | 一次操作 → **逐端列出反馈**（APP UI / 设备 / 后台） | 通过 APP 关机功能正常 |

**异常/边界与响应式不是独立类型，是叠加维度**：六类中任何一类都可以叠加「异常输入、时间边界、横竖屏、分辨率、长文案」，见第五节。

## 二、逐类生成规则（含描述模板）

### 1. 界面交互测试（控件交互）

**公式**：`前置=在 X 界面` + `步骤=触发动作` + `预期=反馈的视觉表现`

预期不能只写「选中成功」，必须写**选中态长什么样**：

| 反面（不可判定） | 正面（可判定） |
|---|---|
| 闪烁选项选中成功 | 闪烁选项框**变蓝**（列表后面的圆点） |
| 跳转成功 | 界面应跳转到设备设置界面 |
| 提示正确 | 应弹出提示信息："长度8位，需要含数字和字母"（**逐字**） |

**三个必答**：
- 跳转类：跳到哪个界面（界面名写全）？
- 状态类：控件状态变化后**视觉属性**是什么（颜色/形状/位置）？
- 时机类：什么时候反馈（立即 / 超时后 / X 秒后不弹）？时间边界单独成一条（如「超过 90 秒后再次提交**不应**弹出提示信息」）。

### 2. UI 元素测试（元素清单）

**公式**：`步骤=查验 X 界面 UI 元素` + `预期=元素枚举清单，每项带视觉属性`

**元素清单的枚举顺序**（按视觉动线，防漏项）：

```
1. 导航/返回类：返回按钮、标题栏
2. 图标类：颜色 + 形状（红色三角形、圆形蓝色背景+白色√、右上角铃铛图标）
3. 输入类：输入框 + 占位符（"获取验证码"按钮属于输入框组合）
4. 提示类：提示文案（逐字写出）
5. 操作类：确认/取消按钮 + 位置（居右/居中）
```

**每项必带**至少一个视觉属性：颜色（蓝/红/灰/白）、形状（圆/三角/圆点）、位置（右上角/居中/居左）、状态（置灰/高亮）。没有视觉属性的元素枚举是「功能清单」不是「UI 清单」。

**收尾一句**：「实际提示框界面应与 UI 原型图一致」——把设计稿兜底写进预期。

### 3. 文字查验测试（文案）

四条子规则：

| 子规则 | 公式 | 例 |
|---|---|---|
| 错别字/敏感词 | 全部文字 → 不应有错别字；不应出现敏感、人身攻击、宗教歧义、种族歧视、性别歧视词汇 | 协议书文字内容应规范 |
| 占位符逐字 | 输入框 → 占位符**逐字**为 X | 占位符应为：Verification Code |
| 文字逐状态颜色 | 每个控件 × 每个状态 → 一种颜色 | 标题黑色；占位符**置灰**；Send 默认**蓝色**；倒计时态**置灰** |
| 多语言版本 | 国内/国外版本 → 各自语言逐字 | 协议书内容应完整覆盖（国内中文显示/国外英文显示） |

**逐状态颜色是这类的主力写法**：一个控件写一条状态-颜色对，不要合并成「颜色正确」。

### 4. 数据展示测试（精度与格式）

**公式**：`数据源（数据库/物模型） → 显示规则（精度/单位/格式） → 对比验证`

| 反面 | 正面 |
|---|---|
| 骑行里程显示正确 | 总里程数据应**四舍五入**显示；数据库存 m，APP 以 km 显示**小数点后两位** |
| 物模型数据正确 | 物模型中右转向灯（5）状态应为：**1**；公英制属性值应为：**0** |

**必答三件**：数据源是什么（数据库字段/物模型属性）、换算规则是什么（单位换算/精度/格式化）、显示值应等于什么（具体值或逐字段比对）。

### 5. 用户体验测试（环境切换）

**公式**：`前置=处于 A 环境（含"过程中"状态）` + `步骤=切换到 B 环境` + `预期=主功能逐项不中断`

- 网络维度成对出题：电信↔WiFi、WiFi↔SIM、2.4G↔5G（**每对一条**，不要合并成"网络切换"）
- 预期逐项：下载能继续 / 包完整 / 安装正常
- 同型扩展：蓝牙断连重连、来电中断、切后台返回

### 6. 模块交互测试（跨端联动）

**公式**：`一次操作 → 每个受影响端各写一条断言`

```
步骤：点击 APP 上的关机按钮
预期：1. APP 按钮 UI 由白色背景变为黑色背景（根据 UI 对比测试）
     2. 滑板车仪表盘熄灭
     3. 滑板车发出蜂鸣声
     4. 不能正常使用滑板车
     5. 系统后台显示滑板车状态变为关闭状态
```

**先枚举受影响端**：APP 界面 / 设备硬件（仪表盘/蜂鸣/指示灯）/ 系统后台状态 / 第三方（IOT 物模型）。一次操作验证几端就写几条，**不允许只写 APP 端**。

## 三、可判定视觉词表（预审第 7 项对 UI 族的附加词表）

UI 族用例的预期必须至少含以下**任一**视觉词（与通用断言标志「应/数值/提示」双轨并行）：

| 维度 | 词表 |
|---|---|
| 颜色 | 黑色 / 白色 / 蓝色 / 红色 / 灰色 / 绿色 / 黄色 / 置灰 / 高亮 / 变蓝 / 变色 |
| 位置 | 居中 / 居左 / 居右 / 左上角 / 右上角 / 底部 / 顶部 |
| 形状/控件 | 图标 / 圆点 / 圆形 / 三角形 / 圆圈 / 插画 / 输入框 / 弹窗 / 复选框 / 列表 |
| 状态/动效 | 选中 / 显示 / 弹出 / 隐藏 / 消失 / 闪烁 / 滚动 / 截断 / 省略 |

**仍不可判定的 UI 措辞**（黑名单同样生效）：美观、合理、协调、大气、流畅——它们是**主观词**，就算写成「界面颜色搭配合理」也不合格，必须落到「标题黑色；占位符置灰；按钮蓝色」这种逐状态断言。

## 四、状态变化的系统性枚举（防漏）

一个控件的完整状态集，按「可交互状态 × 视觉维度」矩阵枚举：

| 状态轴 | 枚举 |
|---|---|
| 交互态 | 默认态 / 按下态（按压反馈） / 选中态 / 禁用态（置灰不可点） / 加载态 |
| 数据态 | 空态（空插画+文案） / 有数据态 / 加载失败态 / 超时态 |
| 过程态 | 倒计时态 / 进度态 / 成功态 / 失败态 |

**生成规则**：写控件用例时，对照此矩阵自问「这个控件有几种状态？每种的颜色/文案/可点击性分别是什么？」——每种状态至少一条用例（或并入元素清单的子项）。

**范例**（一个「获取验证码」按钮的完整状态集）：
- 默认态：蓝色，可点击
- 倒计时态：置灰，文案「60s」，不可点击
- 超时恢复态：恢复蓝色可点击
- 90 秒后再次提交：**不应**弹出提示（时间边界单独成条）

## 五、响应式与异常/边界（叠加维度）

| 维度 | 生成公式 | 例 |
|---|---|---|
| 横竖屏 | 同一界面横屏/竖屏各一条，预期=元素完整 + 布局重排无错位 | 跨竖屏/横屏表现一致 |
| 分辨率 | 典型分辨率各一条，预期=无裁切/无重叠/自适应 | 自由跑横屏适配 1920×1080 与 1280×800 |
| 长文案 | 超长输入 → 省略号/换行，不撑破容器 | 超长昵称末尾省略号截断，字符不被截半 |
| 时间边界 | 阈值前后各一条（如 90 秒内弹提示 / 超过 90 秒不弹） | 超过 90 秒后再次提交获取验证不应弹出提示 |
| 极值输入 | 最长/最短/空/全特殊字符 | 密码含 `!@#$%^&*` 连接成功，字符无丢失 |
| 缺资源 | 断网/弱网/无权限 → 降级提示 | 断网触发播报降级为本地 TTS |

## 六、与功能用例的配比

优秀库的实测配比（可作项目基线）：

| 类型 | 占比 |
|---|---|
| 模块功能测试 | 49% |
| 界面交互测试 | 25% |
| UI 元素测试 | 10% |
| 数据展示测试 | 5% |
| 主流程测试 | 4% |
| 文字查验测试 | 3% |
| 用户体验 / 模块交互 / 性能 | 3% |

**生成时自检**：一个页面型功能点若只有功能用例、没有界面交互与 UI 元素用例，视为 UI 覆盖缺失——补「控件交互反馈」与「元素清单」各 ≥1 条。纯后台/接口功能点可豁免 UI 族（在 `test_type` 用功能/接口类自然区分）。

## 六·五、生成时自检表（每个页面型功能点过一遍）

> v1.11.2 起并入 Step 3 强制流程：页面型功能点产出功能/异常/边界测试点后，**逐行打勾**，缺行即补对应 UI 测试点。纯后台/接口/固件功能点整体豁免（标注「无 UI」）。

| # | 自检项 | 缺失时补什么 |
|---|---|---|
| 1 | 本页每个**可交互控件**（按钮/输入框/开关/列表项）是否都有「触发 → 视觉反馈」测试点？ | 界面交互测试（第二节 1） |
| 2 | 本页是否有一条「UI 元素清单」用例，逐项枚举元素 + 视觉属性？ | UI 元素测试（第二节 2） |
| 3 | 控件的**状态集**是否全覆盖（默认/按下/选中/禁用/加载，见第四节矩阵）？ | 每状态一条，或并入元素清单子项 |
| 4 | 页面文字是否查过错别字/敏感词/占位符逐字/逐状态颜色？ | 文字查验测试（第二节 3） |
| 5 | 页面展示的数据（数值/单位/精度）是否有格式化断言？ | 数据展示测试（第二节 4） |
| 6 | 本功能是否涉及环境切换（网络/蓝牙/前后台）？→ 成对出题 | 用户体验测试（第二节 5） |
| 7 | 一次操作是否影响多端（APP/设备/后台/IOT）？→ 逐端断言 | 模块交互测试（第二节 6） |
| 8 | 横竖屏/分辨率/长文案是否需要覆盖？ | 叠加维度（第五节） |
| 9 | 时间边界（倒计时/超时阈值）前后是否各一条？ | 叠加维度（第五节） |

**量化下限**：页面型功能点 UI 族测试点 ≥2 条（界面交互 + UI 元素各 ≥1）；模块级 UI 族用例占比参考优秀库基线（页面交互型 47%~88%、设备/流程类 30%+），预审 9b 按 `--ui-cover-min`（默认 10%）点名。

## 七、粒度与字段约定

- `test_type` 使用上表六类 + 原功能类（模块功能测试/主流程测试/性能测试/接口测试/数据展示测试）。
- UI 族用例的步骤允许 1 步（「查验 X 界面 UI 元素」），**预期承担全部信息量**——这是 UI 族与功能族的粒度差异：功能族重步骤分解，UI 族重预期枚举。
- 元素清单类预期的编号项数即覆盖的元素数；少于 2 项的「UI 元素」用例视为壳。
- 设计稿是 UI 元素/颜色/间距的**最终依据**：预期应写「与 UI 原型图一致」收尾兜底，具体色值/像素不写死（避免设计稿变更后用例失效）——写「相对属性」（居中/居左/置灰）而非「#1E90FF」。
