# 质量预审：不合格不放行

AI 生成用例最让人不放心的不是慢，而是**你不知道它漏了什么**——覆盖率其实只有 60%、优先级全堆在 P2、P0 寥寥无几。这种结果比没有还烦，因为你还得去检查。

因此本 Skill 在**正式生成前**跑一轮质量预审（Step 5 出口，生成前闸门，运行一次），逐项核查；任何一项不达标先自动修正，改完再输出。

**核心观点：AI 生成用例最大的问题不是慢，而是你不知道它漏了什么。**

---

## 13 项检查 + 默认阈值

前 10 项是**结构闸门**（不达标即阻断）；后 3 项是**密度与深度闸门**（第 11/12/13 项，默认 `warn`，灰度 2 周后再切 `block`），专治"条数够但深度不够"。

| # | 检查项 | 默认阈值 / 规则 | 不达标处理 |
| --- | --- | --- | --- |
| 1 | 需求覆盖率 | ≥ 95%（由 `extract_requirements.py` 生成清单，`map_coverage.py` 映射后由 `--requirement-rules` 传入）。清单默认按「表格合并」落在**需求陈述级**，分母更贴近需求条数而非表格行数（`--no-merge-tables` 可对照旧行为） | 回退补场景 |
| 2 | P0 占比（最高优先级） | 10%–15%（安全攸关软件上调，如 40%–60%） | 重排优先级 |
| 3 | P2 占比 | 35%–45% | 重排优先级 |
| 4 | 每条需求关联 ≥1 种测试设计方法 | `design_method` 非空且合法（6 方法之一或多） | 补方法标注 |
| 5 | 无凭空编造 | 用例 `coverage_rule` 必须落在需求清单内 | 删除 / 转假设 |
| 6 | 无语义重复 | 同 `模块+步骤+预期` 去重 | 合并 |
| 7 | **预期结果可判定** | 预期不得为空；不得命中不可判定词（`合理/美观/友好/流畅/良好/正常显示/工整/尽量/适当/无异常/不卡顿…`）；缺"应 / 数值 / 逐字文案 / 清单编号"等断言标志仅告警 | 改写为断言句 + 具体值 |
| 8 | **标题规范与残缺检查** | 标题 ≤20 字、无序号前缀（`1、`）、无【】、无句末标点；`steps` 不得为空；标题不得含占位残留（`（待XX更新）`/`TBD`/`XXX`）。同模块标题重名仅告警（须靠唯一用例编号区分）；**用例编号重复即阻断**（编号是追溯锚点，见 `naming_rules.md` 第三节） | 重写标题 / 补步骤 / 清占位 / 改编号 |
| 9 | **场景构成配额** | 每功能点 `1 正向 : ≥3 异常·边界·权限`。模块内用例数 ≥4（`--scene-min-cases`）且**无任何异常/边界/权限用例 → 阻断**；负向偏少（`负/正 < 1/3`）或缺权限校验类仅告警 | 补异常/边界/权限用例 |
| 10 | **孤儿用例** | 无 `coverage_rule` 且未标 `exploratory: true` 的用例视为孤儿（反向追溯缺失）。默认 **`--orphan-max 0.0`：任何孤儿即阻断**；设为 0.1 则允许 10% 并降级为告警 | 补 `coverage_rule` / 补需求 / 标 `exploratory: true` |
| 11 | **需求密度**（M1） | 每条需求用例数 ≥ `--min-cases-per-rule`（**默认 0=关闭**；普通项目 4，复杂项目 6）。按 `coverage_rule` 里**写明的 R-ID** 计数，不做文本猜测 | 补该需求下的功能点/测试点 |
| 12 | **方法一致性**（M2） | `design_method` 声称的方法必须有落地证据，否则判**方法虚标**。**默认 `--method-check warn`** | 补证据，或改掉虚标的标签 |
| 13 | **需求级场景配额**（M6） | 每条**需求**至少 1 条异常/边界用例（第 9 项的向下钻取）。**默认 `--scene-rule-mode warn`** | 补该需求的负向用例 |

> 阈值可按项目调整（见下）。例如安全攸关系统常把 P0 占比上调；记忆机制会记住该项目偏好。
> 优先级采用 **P0–P3**（P0=可行性/概念性测试一票否决最高，P1=主流程必测，P2=显示完整性，P3=美观与兼容），与 `priority_p0_p3.md` 口径一致，全技能统一，无 P4。
> 第 7/8 项的实证依据（为什么这么卡）见 `excellent_case_patterns.md`——两条检查分别对应真实优秀库中最常见的两类问题：不可判定预期、占位/残缺/超长标题混入库。
> **第 7 项只是快筛**：黑名单能挡"合理/流畅/美观"，`ASSERT_MARKERS`（含"应/提示/数字"）几乎必过，所以它**挡不住**"应提示账号已锁定"这种测不出阈值写错的弱断言。强度由 Step 5.5 的**强度闸门**兜底（见 `mutation_review.md`，P0 规则 <90% 阻断），不要把第 7 项当强度保证。
> 第 9 项口径见 `testpoint_checklist.md` 第二节（四类场景强制配额）；模块级下钻评审见 `coverage_audit.md`。
> 第 10 项（孤儿用例）是**反向追溯**：需求→用例查漏测，用例→需求查"为什么存在"。口径与 RTM 输出（Excel 第二 sheet）见 `coverage_audit.md`「双向追溯」。
> **第 11/12/13 项是密度与深度闸门，默认 `warn`**：先用真实库回放看命中率，确认无误伤再切 `block`。切 `block` 前必须过配套回归——**规范样例必须 exit 0 零误伤，反例必须逐条命中**。

### 第 11 项：为什么必须逐需求卡密度

第 9 项按**模块**聚合，只要模块合计有负向就放行——所以会出现"一条需求 4 条、模块里另一条需求 8 条"的掩盖。实测一个 196 条 / 47 需求的库：**33 条需求恰好 4 条（70%）**，模块级看起来全绿，逐需求一卡却是 **44/47 不达标、缺口 83 条**。第 11 项就是把这层掩盖拆掉。

```bash
# 复杂项目：每条需求至少 6 条
python scripts/prescreen.py cases.json --requirement-rules rules.json \
       --min-cases-per-rule 6 --density-mode block
# 单字段型/确实只值 2~3 条的简单需求先豁免，避免"为了过闸门硬凑"
python scripts/prescreen.py cases.json --requirement-rules rules.json \
       --min-cases-per-rule 6 --density-exempt R-039,R-038
```

> **密度闸门必须和等价类矩阵（M3）配套**：没有矩阵，密度闸门只会逼出"同一条需求复制 6 遍"；有矩阵，6 条才各有其类。见 `workflow.md` Step 3.5。

### 第 12 项：方法一致性的四条判定（只看步骤+预期，标题不作证据）

| 声称方法 | 落地证据 | 不满足时 |
| --- | --- | --- |
| 边界值分析 | 步骤/预期含**比较·极值词**（`大于/小于/≥/≤/超过/上限/下限/最大/最小/边界/临界/阈值`）**或** `0·100` 边界字面量（`0%`/`0 km/h`/`100%`/满电满格），**且**含具体数字 | 判**虚标** |
| 等价类划分 | `test_data` ≥2 个取值，或正文含类归属词（`有效类/无效类/合法/非法/边界外/异常类/取值/枚举`） | ≥2 值→通过；**仅 1 值→记「欠展开」**（告警，不判虚标）；0 值→判虚标 |
| 判定表法 / 正交分析法 | 步骤含 ≥2 个条件维度（条件线索句，或一行内 ≥3 个 `/` 并列取值） | 判**虚标** |
| 场景法 / 状态迁移法 / 错误推测 | 无结构化判据 | 不检查 |

> **标题不算证据**：`「下载完成不等于安装」` 标题含"等于"，但步骤和预期里没有任何边界断言，判虚标才对——标题是标签，不是断言。
> **「欠展开」与「虚标」必须分开**：前者是方法用了但没做透（该补矩阵），后者是标签造假（该删标签或补真用例）。混为一谈会把正常用例判成造假，闸门就没人信了。实测 196 条库：虚标 10 条（全为边界值）、欠展开 22 条（等价类仅枚举 1 类）。

## 执行

```bash
# 前置：从 PRD 抽取规则并映射到用例
python scripts/extract_requirements.py PRD.md -o ./out
python scripts/map_coverage.py cases.json ./out/requirements.json -o cases.json

# 全部 13 项（推荐，覆盖率检查需需求清单）
python scripts/prescreen.py cases.json --requirement-rules ./out/requirement_rules.json

# 仅结构闸门（前 10 项；无需求清单时）
python scripts/prescreen.py cases.json

# 密度与深度闸门打开（复杂项目建议值）
python scripts/prescreen.py cases.json --requirement-rules ./out/requirement_rules.json \
       --min-cases-per-rule 6 --density-mode block --method-check block --scene-rule-mode block

# 单个闸门关闭（灰度期只想看某一项）
python scripts/prescreen.py cases.json --method-check off

# 阈值可调（安全攸关项目示例：P0 占比上调）
python scripts/prescreen.py cases.json --p0-min 0.40 --p0-max 0.60

# 场景构成门槛（模块用例数少于该值不判负向缺失）
python scripts/prescreen.py cases.json --scene-min-cases 6

# 孤儿用例阈值放宽（默认 0.0=任何孤儿即阻断；0.1=允许 10% 并降级为告警）
python scripts/prescreen.py cases.json --orphan-max 0.1
```

- **全过** → 进入下一阶段 / 输出。
- **单项不达标** → 打印修正建议并退出码 `1`，触发自动修正后重跑。

## 三个检查点（用户只需确认这三处）

0. **检查点⓪**：《测试分析报告》是否确认（需求理解 / 信息缺口 / 测试范围与优先级）——见 `analysis_gate.md`，未确认不生成。
1. **检查点①**：预审阈值是否适用本项目（如 P0 区间、覆盖率基线）。
2. **检查点②**：终稿是否导出 XMind（主产物始终是 Excel）。

其余全自动，用户不在中间环节介入。

## 与评分（score_testcases.py）的关系

- **预审（prescreen）** 发生在生成前：保证"结构合理、不漏不重、方法到位"，是**放行闸门**。
- **评分（score_testcases.py）** 发生在生成后：逐条 0–100 量化（覆盖/准确/可执行/优先级），是**质量终审**。
- 两者互补：预审挡住"整体结构问题"，评分挡住"单条质量问题"。
