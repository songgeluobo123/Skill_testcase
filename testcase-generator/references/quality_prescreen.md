# 质量预审：不合格不放行

AI 生成用例最让人不放心的不是慢，而是**你不知道它漏了什么**——覆盖率其实只有 60%、优先级全堆在 P2、P0 寥寥无几。这种结果比没有还烦，因为你还得去检查。

因此本 Skill 在**正式生成前**跑一轮质量预审（Step 5 出口，生成前闸门，运行一次），逐项核查；任何一项不达标先自动修正，改完再输出。

**核心观点：AI 生成用例最大的问题不是慢，而是你不知道它漏了什么。**

## 14 项检查 + 默认阈值

前 10 项是**结构闸门**（不达标即阻断）；后 4 项是**密度与深度闸门**，专治"条数够但深度不够"。

> **命令行默认生效只有 13 项**：第 12/13/14 项默认 `warn`（只告警不阻断），**第 11 项默认关闭**（`--min-cases-per-rule 0`）。想真正启用密度闸门必须显式传参，否则它只是个不会响的开关——这是本项目最容易"以为开了其实没开"的地方。
>
> **所以 Step 5 的命令模板把四项全部硬写成 `block`**，不给"忘了传参"留口子。

| # | 检查项 | 默认阈值 / 规则 | 不达标处理 |
| --- | --- | --- | --- |
| 1 | 需求覆盖率 | ≥ 95%（由 `extract_requirements.py` 生成清单，`map_coverage.py` 映射后由 `--requirement-rules` 传入）。清单默认按「表格合并」落在**需求陈述级**，分母更贴近需求条数而非表格行数（`--no-merge-tables` 可对照旧行为） | 回退补场景 |
| 2 | P0 占比（最高优先级） | 10%–25%（安全攸关软件上调，如 40%–60%） | 重排优先级 |
| 3 | P2 占比 | 25%–40% | 重排优先级 |
| 4 | 每条需求关联 ≥1 种测试设计方法 | `design_method` 非空且合法（6 方法之一或多）。**全库该字段都为空 → 整项跳过**（真实项目库常没有这一列，逐条判违规会得到 100% 失败） | 补方法标注 |
| 5 | 无凭空编造 | 用例 `coverage_rule` 必须落在需求清单内 | 删除 / 转假设 |
| 6 | 无语义重复 | 同 `模块+前置条件+步骤+预期` 去重（**前置不同即视为不同用例**） | 合并 |
| 7 | **预期结果可判定** | 预期不得为空；不得命中不可判定词（`合理/美观/友好/流畅/良好/正常显示/工整/尽量/适当/无异常/不卡顿…`）；缺"应 / 数值 / 逐字文案 / 清单编号"等断言标志仅告警 | 改写为断言句 + 具体值 |
| 8 | **标题规范与残缺检查** | 标题 ≤ `--title-max` 字（默认 30，收紧口径的项目传 20）、无序号前缀（`1、`）、无【】、无句末标点；`steps` 不得为空；标题不得含占位残留（`（待XX更新）`/`TBD`/`XXX`）。同模块标题重名仅告警（须靠唯一用例编号区分）；**用例编号重复即阻断**（编号是追溯锚点，见 `naming_rules.md` 第三节） | 重写标题 / 补步骤 / 清占位 / 改编号 |
| 9 | **场景构成配额** | 每功能点 `1 正向 : ≥3 异常·边界·权限`。模块内用例数 ≥4（`--scene-min-cases`）且**无任何异常/边界/权限用例 → 阻断**；负向偏少（`负/正 < 1/3`）或缺权限校验类仅告警 | 补异常/边界/权限用例 |
| 10 | **孤儿用例** | 无 `coverage_rule` 且未标 `exploratory: true` 的用例视为孤儿（反向追溯缺失）。默认 **`--orphan-max 0.0`：任何孤儿即阻断**；设为 0.1 则允许 10% 并降级为告警。**全库都没有 `coverage_rule` 且未提供 `--requirement-rules` → 整项跳过**（这份库不做需求追溯，逐条判孤儿就是 100%） | 补 `coverage_rule` / 补需求 / 标 `exploratory: true` |
| 11 | **需求密度**（M1） | 每条需求用例数 ≥ `--min-cases-per-rule`（**默认 0=关闭**；普通项目 4，复杂项目 6）。按 `coverage_rule` 里**写明的 R-ID** 计数，不做文本猜测 | 补该需求下的功能点/测试点 |
| 12 | **方法一致性**（M2） | `design_method` 声称的方法必须有落地证据，否则判**方法虚标**。**默认 `--method-check warn`** | 补证据，或改掉虚标的标签 |
| 13 | **需求级场景配额**（M6） | 每条**需求**至少 1 条异常/边界用例（第 9 项的向下钻取）。**只有 0 条负向才阻断**；`0 < 负向 < --min-neg-per-rule`（默认 3）仅告警"负向偏少"，不阻断。**默认 `--scene-rule-mode warn`** | 补该需求的负向用例 |
| 14 | **范围性用例**（M4 兜底） | 步骤含 `逐一/逐个/依次/分别/遍历/逐项/逐条/全部/所有/每个/各个` **且**并列对象 ≥ `--range-min-objs`（默认 3）**且**预期只有 1 条断言 → 判「一条用例吃掉 N 个场景」。备注列已逐项展开的降级为提示。**默认 `--range-mode warn`** | 拆条，或在备注列逐项展开场景 |

> 阈值可按项目调整（见下）。例如安全攸关系统常把 P0 占比上调；记忆机制会记住该项目偏好。
> 优先级采用 **P0–P3**（P0=可行性/概念性测试一票否决最高，P1=主流程必测，P2=显示完整性，P3=美观与兼容），与 `priority_p0_p3.md` 口径一致，全技能统一，无 P4。
> 第 7/8 项的实证依据（为什么这么卡）见 `excellent_case_patterns.md`——两条检查分别对应真实优秀库中最常见的两类问题：不可判定预期、占位/残缺/超长标题混入库。
> **第 7 项只是快筛**：黑名单能挡"合理/流畅/美观"，`ASSERT_MARKERS`（含"应/提示/数字"）几乎必过，所以它**挡不住**"应提示账号已锁定"这种测不出阈值写错的弱断言。强度由 Step 5.5 的**强度闸门**兜底（见 `mutation_review.md`，P0 规则 <90% 阻断），不要把第 7 项当强度保证。
> 第 9 项口径见 `testpoint_checklist.md` 第二节（四类场景强制配额）；模块级下钻评审见 `coverage_audit.md`。
> 第 10 项（孤儿用例）是**反向追溯**：需求→用例查漏测，用例→需求查"为什么存在"。口径与 RTM 输出（Excel 第二 sheet）见 `coverage_audit.md`「双向追溯」。
> **第 6 项指纹必须含前置条件**（v1.9.8 起）：真实库报过一组"重复"——`TC-首页-006`（前置=已进入「本周训练」界面）与 `TC-首页-010`（前置=已进入「四周训练」界面），步骤与预期逐字相同。但那是两个入口，而 `case_design.md` 第七节自己就要求「多入口 → 一律拆条」。漏掉前置等于让工具推翻它自己刚下的设计规范。**本项是 `fails` 阻断，误报代价比 `warn` 大得多**——会逼着人把刚按要求拆开的用例再删回去。
> **第 11/12/13/14 项是密度与深度闸门，默认 `warn`**：先用真实库看命中率，确认无误伤再切 `block`。切 `block` 前必须过配套回归——**规范样例必须 exit 0 零误伤，反例必须逐条命中**。

### 第 14 项：为什么"数条数"数不出假覆盖

第 9/11/13 项全都只在**数条数**：条数够、每条都有负向，就放行。但下面这条用例能同时满足它们：

> **步骤**：依次点击 首页、课程库、个人档案、训练记录
> **预期**：1. 各页面正常显示

它在第 9 项里算 1 条正向、第 11 项里给该需求 +1 条、第 13 项里不欠负向——**而它实际是 4 个场景压成 1 条，且只有 1 条断言**。这就是"4 条用例覆盖 16 个场景"能全绿通过的原因，也是 13 项闸门里**唯一没有兜底**的缺口。

第 14 项的判定（三条同时成立才算强证据）：

| 条件 | 说明 |
| --- | --- |
| 步骤含范围词 | `逐一/逐个/依次/分别/遍历/逐项/逐条/全部/所有/每个/各个`；**只在 steps 里找，预期里的"逐一显示"是合法表述不算** |
| 并列对象 ≥ `--range-min-objs`（默认 3） | 只按**顿号与斜杠**切分。不切「和/及/与」——这三个字在中文里高频出现在词内部（"和值""及时""与其"），切了必然误伤 |
| 预期断言 ≤ 1 条 | 预期有 3 条断言，说明 3 个对象各有着落，不算范围性用例 |

**「预期断言条数」怎么数（v1.9.7 起）**：取 `max(换行/数组条数, 顺序编号条目数)`。

真实 Excel 用例库常把多条断言塞进同一个单元格，甚至把 `2.` 直接贴在上句末尾（`…无中文残留2. 特殊字符…`），既不换行也不空格。**只数换行会把 5 条断言当成 1 条**，把正常的多断言用例全判成范围性用例——某真实库实测：只数换行命中 234 条，改本口径后 14 条，**220 条是假阳性**。

编号计数只认 `1. 2. 3.` **递增序列，断链即停**，且 `(?!\d)` 挡掉 `3.8-4.4 km/h`、`v1.0`、`1.15 秒` 这类数值——宁可少数（少报），不能多数（把真范围性用例洗成合格）。

**豁免出口**：备注列已逐项展开的（`亮度=50 生效；音量=80 生效；…`），降级为弱提示不再阻断。这是 `case_design.md` 第七节明确允许的「预期同构的批量校验」写法，不给出口就会误伤正常用例。

```bash
# 关闭（不建议：这是当前唯一没有兜底的敞口）
python scripts/prescreen.py cases.json --range-mode off
# 收紧到 2 个并列对象即报（小项目）
python scripts/prescreen.py cases.json --range-min-objs 2 --range-mode block
```

### 退出码契约（全部脚本统一）

| 码 | 含义 | 该怎么办 |
| --- | --- | --- |
| `0` | 通过（可能仅有告警） | 继续下一步 |
| `1` | **有项目不达标** | 改用例 |
| `2` | 输入/参数错误（文件不存在、JSON 坏、需求清单读不到） | 查路径与参数，**别改用例** |
| `3` | **脚本自身崩溃** | 这是技能 bug，改用例永远改不好；带 `stderr` 堆栈报维护者 |
| `4` | **环境缺依赖**（如缺 `openpyxl`） | 装包或换解释器，**别改用例也别改参数** |

> **为什么必须有 `3`**：早期所有非 0 都返回 `1`。`steps` 传数组导致 `norm()` 抛 `TypeError` 那次，脚本崩在**第 6 项**、第 7~13 项全没跑，退出码却是 `1`——看起来完全像"用例不达标"，实际是脚本挂了。**一个不会区分"你的错"和"我的错"的闸门，比没有闸门更浪费时间。**
>
> **为什么又加了 `4`**：`to_excel.py` 原来把"缺 `openpyxl`"报成 `2`（参数错）。调用方看到 `2` 会去查路径、调参数，永远修不好——因为该做的是 `pip install`。同一个"非 0"背后是三种完全不同的动作，就必须有三种码。
>
> 自查口诀：输出里既没有 `=== 预审全部通过 ===` 也没有 `=== 预审不通过 ===` 的，就是崩溃，去 `stderr` 找 Traceback，别改用例。


### 字段整体缺失 ≠ 字段填错（第 4 / 10 项的跳过条件）

真实项目库的列集合各不相同。某份 15 列的正式库**没有**「设计方法」列，也**没有**「需求编号」列——
按「逐条判违规」跑，第 4 项和第 10 项会得到 **100% 失败**（799/799）。这不是用例有问题，是字段形态不同。

判据与处理：

| 情况 | 处理 | 理由 |
| --- | --- | --- |
| 全库该字段都为空（第 4 项 `design_method`） | 整项**跳过**，打印 `[–]` | 库里没有这个概念，判它惩罚的是"库的形态"，不是"用例的质量" |
| 全库无 `coverage_rule` **且**未给 `--requirement-rules`（第 10 项） | 整项**跳过**，打印 `[–]` | 没给需求清单就无法谈"反向追溯缺失"，每条都算孤儿=100%，判了没有信息量 |
| 部分填了、部分没填（任一项） | **照常判**，只算"该填却没填/填错"的那些 | 跳过不能变成免罚出口 |

**跳过必须可见**：输出末尾单独一段「已跳过的闸门（本库字段形态不支持，不代表通过）」。静默跳过等于把闸门关掉还不报警，比误报更危险——使用者会以为"这项过了"。

> 反向的坑同样要防：给了 `--requirement-rules` 就说明这份库要按需求追溯，此时"全库无 `coverage_rule`"是**真孤儿**，不许跳过。

### 整数粒度陷阱：占比阈值为什么必须有补偿

条数是整数，占比区间未必有整数解。默认 P0∈[10%,25%] 比较宽，多数库都有解；但**区间一旦收窄就会无解**——安全攸关项目常用 P0∈[40%,45%]：

| 总条数 | 区间 | 可行 P0 条数 | 说明 |
| --- | --- | --- | --- |
| 20 | [10%,25%] | 2~5 条 | 有解，不触发补偿 |
| 13 | [40%,45%] | **无** | 5 条=38.5%（低于 40%）、6 条=46.2%（高于 45%） |
| 12 | [40%,45%] | 5 条 | 41.7%，有解 |
| 7 | [40%,45%] | 3 条 | 42.9%，有解 |

这类库**无论怎么排优先级都过不了闸门**——这是闸门的错，不是用例的错。所以第 2/3 项内置整数粒度补偿：**仅当该区间在该总条数下确实不存在任何整数解时**，才按 `--ratio-tolerance`（单位：条，默认 0.5）放宽，并在输出里显式打「整数粒度补偿」标记 + 追加一条告警。

> **区间越窄越容易无解**：把 `--p0-max` 从 0.25 收到 0.15 这类操作，会让 5/6/11/12 条的小库立刻掉进无解区。改窄区间前先用上式算一遍。

```bash
# 关闭补偿（不建议：窄区间 + 小样本会被判死）
python scripts/prescreen.py cases.json --ratio-tolerance 0
```

补偿**只救"区间本身无解"**，不救真的排错：20 条库 0 条 P0 依然失败。判据是 `any(lo <= i/n <= hi for i in 0..n)`，逻辑在 `prescreen.py` 第 2/3 项，回归见 `test_schema_contract.py` D3 组。

### 输入字段契约（两个历史坑，已修，勿回退）

| 坑 | 现象 | 现在 |
| --- | --- | --- |
| **标题字段分裂** | 规范与 `to_excel.py` 用 `name`，`prescreen`/`coverage_audit` 只读 `title` → 按规范写出的用例被判「标题为空」全量阻断 | `name` 优先、`title` 兜底，全链路同口径 |
| **steps 写成数组** | `norm()` 只吃 `str`，遇数组抛 `TypeError` → 第 6 项崩溃，第 7~13 项**全部不执行**，退出码 1 被误读成「预审不通过」 | `norm()` 自动把 list 归一化成换行字符串 |

> 这两个坑长期没被发现，是因为旧回归夹具**同时写了 `name` 和 `title`、且 steps 用字符串**——夹具比实现更宽容，就把 bug 盖住了。写回归时`只给规范字段、不给别名`才是有效验证。


### 第 11 项：为什么必须逐需求卡密度

第 9 项按**模块**聚合，只要模块合计有负向就放行——所以会出现"一条需求 4 条、模块里另一条需求 8 条"的掩盖。实测一个 196 条 / 47 需求的库：**33 条需求恰好 4 条（70%）**，模块级看起来全绿，逐需求一卡却是 **44/47 不达标、缺口 83 条**。第 11 项就是把这层掩盖拆掉。

```bash
# 复杂项目：每条需求至少 6 条
python scripts/prescreen.py cases.json --requirement-rules rules.json \
       --min-cases-per-rule 6 --density-mode block
# 单字段型/确实只值 2~3 条的简单需求先豁免，避免"为了过闸门硬凑"
python scripts/prescreen.py cases.json --requirement-rules rules.json \
       --min-cases-per-rule 6 --density-exempt R-039,R-038
```

> **密度闸门必须和等价类矩阵（M3）配套**：没有矩阵，密度闸门只会逼出"同一条需求复制 6 遍"；有矩阵，6 条才各有其类。见 `workflow.md` Step 3.5。

### 第 12 项：方法一致性的四条判定（只看步骤+预期，标题不作证据）

| 声称方法 | 落地证据 | 不满足时 |
| --- | --- | --- |
| 边界值分析 | 步骤/预期含**比较·极值词**（`大于/小于/≥/≤/超过/上限/下限/最大/最小/边界/临界/阈值`）**或** `0·100` 边界字面量（`0%`/`0 km/h`/`100%`/满电满格），**且**含具体数字 | 判**虚标** |
| 等价类划分 | `test_data` ≥2 个取值，或正文含类归属词（`有效类/无效类/合法/非法/边界外/异常类/取值/枚举`） | ≥2 值→通过；**仅 1 值→记「欠展开」**（告警，不判虚标）；0 值→判虚标 |
| 判定表法 / 正交分析法 | 步骤含 ≥2 个条件维度（条件线索句，或一行内 ≥3 个 `/` 并列取值） | 判**虚标** |
| 场景法 / 状态迁移法 / 错误推测 | 无结构化判据 | 不检查 |

> **标题不算证据**：`「下载完成不等于安装」` 标题含"等于"，但步骤和预期里没有任何边界断言，判虚标才对——标题是标签，不是断言。
> **词表可外置**：中文表达千变万化，固定词表必然漏判。项目侧用 `--method-lexicon lex.json` 按领域术语增补（`{"boundary":["触顶"],"eq_class":[...],"cond":[...],"boundary_literal":"正则"}`）。
> **是合并不是替换**：只写要增补的词，内置词表不会被顶掉——这一点有回归钉着，因为「加了自己的词反而丢内置词」是最容易发生、最难察觉的配置事故。
> **「欠展开」与「虚标」必须分开**：前者是方法用了但没做透（该补矩阵），后者是标签造假（该删标签或补真用例）。混为一谈会把正常用例判成造假，闸门就没人信了。实测 196 条库：虚标 10 条（全为边界值）、欠展开 22 条（等价类仅枚举 1 类）。

## 执行

```bash
# 前置：从 PRD 抽取规则并映射到用例
python scripts/extract_requirements.py PRD.md -o ./out
python scripts/map_coverage.py cases.json ./out/requirements.json -o cases.json

# 全部 14 项（推荐，覆盖率检查需需求清单）
python scripts/prescreen.py cases.json --requirement-rules ./out/requirement_rules.json

# 仅结构闸门（前 10 项；无需求清单时）
python scripts/prescreen.py cases.json

# 【Step 5 标准模板】四个深度闸门全部显式 block —— 也是唯一推荐的生产用法
python scripts/prescreen.py cases.json --requirement-rules ./out/requirement_rules.json \
       --min-cases-per-rule 6 --density-mode block --method-check block \
       --scene-rule-mode block --range-mode block

# 灰度期：只想先看某一项命中多少，不阻断
python scripts/prescreen.py cases.json --method-check warn

# 单个闸门关闭（只在排障时用，别写进流程）
python scripts/prescreen.py cases.json --method-check off

# 阈值可调（安全攸关项目示例：P0 占比上调）
python scripts/prescreen.py cases.json --p0-min 0.40 --p0-max 0.60

# 场景构成门槛（模块用例数少于该值不判负向缺失）
python scripts/prescreen.py cases.json --scene-min-cases 6

# 需求级负向条数告警线（第 13 项：0 条才阻断，1~2 条只告警；设 0 可静音该告警）
python scripts/prescreen.py cases.json --requirement-rules rules.json --min-neg-per-rule 3

# 范围性用例门槛（第 14 项：默认 3 个并列对象即报；小项目可降到 2）
python scripts/prescreen.py cases.json --range-min-objs 2 --range-mode block

# 孤儿用例阈值放宽（默认 0.0=任何孤儿即阻断；0.1=允许 10% 并降级为告警）
python scripts/prescreen.py cases.json --orphan-max 0.1
```

- **全过（exit 0）** → 进入下一阶段 / 输出。
- **单项不达标（exit 1）** → 打印修正建议，触发自动修正后重跑。
- **参数/输入错误（exit 2）** → 改命令行，不要改用例。
- **脚本崩溃（exit 3）** → 技能 bug，带 `stderr` 报维护者。

## 三个检查点（用户只需确认这三处）

0. **检查点⓪**：《测试分析报告》是否确认（需求理解 / 信息缺口 / 测试范围与优先级）——见 `analysis_gate.md`，未确认不生成。
1. **检查点①**：预审阈值是否适用本项目（如 P0 区间、覆盖率基线）。
2. **检查点②**：终稿是否导出 XMind（主产物始终是 Excel）。

其余全自动，用户不在中间环节介入。

## 与评分（score_testcases.py）的关系

- **预审（prescreen）** 发生在生成前：保证"结构合理、不漏不重、方法到位"，是**放行闸门**。
- **评分（score_testcases.py）** 发生在生成后：逐条 0–100 量化（覆盖/准确/可执行/优先级），是**质量终审**。
- 两者互补：预审挡住"整体结构问题"，评分挡住"单条质量问题"。
