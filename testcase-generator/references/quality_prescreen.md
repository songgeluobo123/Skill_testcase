# 质量预审：不合格不放行

AI 生成用例最让人不放心的不是慢，而是**你不知道它漏了什么**——覆盖率其实只有 60%、优先级全堆在 P2、P0 寥寥无几。这种结果比没有还烦，因为你还得去检查。

因此本 Skill 在**正式生成前**跑一轮质量预审（Step 5 出口，生成前闸门，运行一次），逐项核查；任何一项不达标先自动修正，改完再输出。

**核心观点：AI 生成用例最大的问题不是慢，而是你不知道它漏了什么。**

## 9 项检查 + 默认阈值

| # | 检查项 | 默认阈值 / 规则 | 不达标处理 |
| --- | --- | --- | --- |
| 1 | 需求覆盖率 | ≥ 95%（由 `extract_requirements.py` 生成清单，`map_coverage.py` 映射后由 `--requirement-rules` 传入）。清单默认按「表格合并」落在**需求陈述级**，分母更贴近需求条数而非表格行数（`--no-merge-tables` 可对照旧行为） | 回退补场景 |
| 2 | P0 占比（最高优先级） | 10%–15%（安全攸关软件上调，如 40%–60%） | 重排优先级 |
| 3 | P2 占比 | 35%–45% | 重排优先级 |
| 4 | 每条需求关联 ≥1 种测试设计方法 | `design_method` 非空且合法（6 方法之一或多） | 补方法标注 |
| 5 | 无凭空编造 | 用例 `coverage_rule` 必须落在需求清单内 | 删除 / 转假设 |
| 6 | 无语义重复 | 同 `模块+步骤+预期` 去重 | 合并 |
| 7 | **预期结果可判定** | 预期不得为空；不得命中不可判定词（`合理/美观/友好/流畅/良好/正常显示/工整/尽量/适当/无异常/不卡顿…`）；缺"应 / 数值 / 逐字文案 / 清单编号"等断言标志仅告警 | 改写为断言句 + 具体值 |
| 8 | **标题规范与残缺检查** | 标题 ≤20 字、无序号前缀（`1、`）、无【】、无句末标点；`steps` 不得为空；标题不得含占位残留（`（待XX更新）`/`TBD`/`XXX`）。同模块标题重名仅告警（须靠唯一用例编号区分）；**用例编号重复即阻断**（编号是追溯锚点，见 `naming_rules.md` 第三节） | 重写标题 / 补步骤 / 清占位 / 改编号 |
| 9 | **场景构成配额** | 每功能点 `1 正向 : ≥3 异常·边界·权限`。模块内用例数 ≥4（`--scene-min-cases`）且**无任何异常/边界/权限用例 → 阻断**；负向偏少（`负/正 < 1/3`）或缺权限校验类仅告警 | 补异常/边界/权限用例 |

> 阈值可按项目调整（见下）。例如安全攸关系统常把 P0 占比上调；记忆机制会记住该项目偏好。
> 优先级采用 **P0–P3**（P0=可行性/概念性测试一票否决最高，P1=主流程必测，P2=显示完整性，P3=美观与兼容），与 `priority_p0_p3.md` 口径一致，全技能统一，无 P4。
> 第 7/8 项的实证依据（为什么这么卡）见 `excellent_case_patterns.md`——两条检查分别对应真实优秀库中最常见的两类问题：不可判定预期、占位/残缺/超长标题混入库。
> 第 9 项口径见 `testpoint_checklist.md` 第二节（四类场景强制配额）；模块级下钻评审见 `coverage_audit.md`。

## 执行

```bash
# 前置：从 PRD 抽取规则并映射到用例
python scripts/extract_requirements.py PRD.md -o ./out
python scripts/map_coverage.py cases.json ./out/requirements.json -o cases.json

# 全部 9 项（推荐，覆盖率检查需需求清单）
python scripts/prescreen.py cases.json --requirement-rules ./out/requirement_rules.json

# 仅优先级/方法/重复/可判定性/标题/场景构成检查（无需求清单时）
python scripts/prescreen.py cases.json

# 阈值可调（安全攸关项目示例：P0 占比上调）
python scripts/prescreen.py cases.json --p0-min 0.40 --p0-max 0.60

# 场景构成门槛（模块用例数少于该值不判负向缺失）
python scripts/prescreen.py cases.json --scene-min-cases 6
```

- **全过** → 进入下一阶段 / 输出。
- **单项不达标** → 打印修正建议并退出码 `1`，触发自动修正后重跑。

## 三个检查点（用户只需确认这三处）

0. **检查点⓪**：《测试分析报告》是否确认（需求理解 / 信息缺口 / 测试范围与优先级）——见 `analysis_gate.md`，未确认不生成。
1. **检查点①**：预审阈值是否适用本项目（如 P0 区间、覆盖率基线）。
2. **检查点②**：终稿是否导出 XMind（主产物始终是 Excel）。

其余全自动，用户不在中间环节介入。

## 与评分（score_testcases.py）的关系

- **预审（prescreen）** 发生在生成前：保证"结构合理、不漏不重、方法到位"，是**放行闸门**。
- **评分（score_testcases.py）** 发生在生成后：逐条 0–100 量化（覆盖/准确/可执行/优先级），是**质量终审**。
- 两者互补：预审挡住"整体结构问题"，评分挡住"单条质量问题"。
